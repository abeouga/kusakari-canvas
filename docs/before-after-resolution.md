# Before / After の解像度変換（2026-10-19）

追記：利用者の追加要件により、新規生成は `full_frame_v3` へ更新しました。
全景を保持する入力変換は維持し、出力の元写真寸法への縮小は廃止しています。
現行仕様と検証結果は [完成イメージの簡素化と生成解像度の保持](image-studio.md) を参照。
以下は最初の `full_frame_v2` 修正時点の記録です。

## Context

旧 `full_frame_v1` は小さい写真を拡大せず、右下に白い余白を足して最低1024×1024pxにした。
返却画像は左上から元写真の幅・高さだけ切り出していた。生成側が全キャンバスへ構図を
広げると、大部分を捨てて左上だけをAfterとして保存してしまう。
259×194pxの保存済みBefore / Afterを確認したところ、両者の画像寸法・表示枠・
`object-fit: contain` は一致していたが、AfterのPNG自体が建物の一部だけになっていた。
通常環境には切り出し前の生成画像を保存していないため、モデルの生出力は未確認。
CSS変更だけで保存画像の欠落部分を復元できる問題ではない。

## Decision

- 新しい生成結果を `full_frame_v2` と識別する。DB列の変更・既存履歴の上書きはしない。
- シーン全体をAPI用サイズへリサイズする。白い余白の追加と左上切り出しはしない。
  小さい写真は約1M画素へ拡大し、16px単位の丸めで縦横比を近似する。
  アプリの上限（長辺2048px、総画素3,686,400）は維持する。
  3:1を超える縦長・横長は、構図を潰す代用ではなく送信前に明示的に拒否する。
- Before・遮蔽補助画像・編集マスク・植物の座標と範囲を同じ縦横倍率で変換する。
  編集余裕幅は元写真の座標で適用後、マスクを最近傍法で変換する。
  庭のJSON、写真、メートル単位の配置、商品参考画像は変更しない。
- 生成結果の全体を元写真の幅・高さへリサイズして保存する。16px丸めのわずかな
  縦横比の差も往復変換で元に戻す。要求と異なる返却サイズは従来どおり拒否し、
  勝手な切り出しで採用しない。
- モデル・品質・参考商品選択は変更しない。生成方式以外の過去の品質評価条件は
  凍結したまま保管する。旧前処理は凍結済み評価を検証するためだけに残し、通常生成では使わない。
- 比較表示は共通の枠と `object-fit: contain` を維持する。異なる自然解像度でも全体を収める。
  旧方式の小さい画像には、欠落時の再生成案内を表示する。

寸法制約は公式OpenAIドキュメント（2026-10-19確認）に照合した。
https://developers.openai.com/api/docs/guides/image-prompting
https://developers.openai.com/api/reference/resources/images/methods/edit

## Alternatives

- CSSでAfterを縮小するだけ：保存時に失われた画素が戻らないため不採用。
- 旧入力の白い余白を残して全体縮小：出力が余白を維持した場合に庭が極端に小さくなるため不採用。
- 既存Afterの補完・自動再生成：元の生成結果の復元にはならず、利用者の履歴変更と追加料金を伴うため実行しない。

## Consequences

新規生成の画面・座標・保存画像で同じ全景を扱う。元の低解像度写真の情報量は増えない。
AI自身による構図変更や植物サイズの誤りを保証して解決するものではない。
既存の切り出された履歴は保持され、修正版での再生成が必要となる。
旧評価計画は入力ハッシュの差異により新処理での有料送信を拒否する。

## Verification plan / independent checks rationale

実API・専用MySQL・Chromiumで履歴保存、再読み込み、スライダー、狭い画面、PNG取得を確認する。
低解像度・縦長・横長の人工画像に四隅と中央の目印を置き、生成側解像度から元画像へ戻す
実処理を適用した結果を保存する。人工画像はAIの生成成功・品質評価として扱わない。

有料の非決定的なAI出力に四隅の色、マスク、透明度、返却寸法違反を指定できないため、
これらの失敗条件は独立した画素検証を併用する。特に旧実装の左上切り出しでは四隅の
色と中心点が失われることを回帰条件とする。座標・マスク・補助画像の倍率一致、同寸法時の
画素不変、形式・透明度・容量の拒否も確認する。正常系APIをモックせず、有料生成は実行しない。

## Verification results

- `verification.verify_ai_frame`：259×194、194×259、320×180を含む10寸法で四隅・中央を保持。
  縦横別倍率での座標変換、家具を保護するマスク、元JSON不変、同寸法の画素不変を確認。
  8MB超の生成PNGと、不正サイズ・透明PNG・形式・容量の拒否も確認した。
- `playwright.before-after.config.ts`：実Canvas/EC API、専用MySQL、Chromiumで3ケース成功。
  変換済み人工画像の履歴保存・再読込、全景の画素、スライダー端点、390px幅、PNGダウンロードを確認。
  さらに表示部だけに異なる自然解像度の画像を入れる独立表示検査で、共通枠とcontainを確認。
  人工画像による幾何変換・保存・表示の検証であり、実AIの品質検証ではない。
- 保存後のスクリーンショットで四隅と中央を目視確認。検証用の庭・履歴・空カートだけを除去し、
  専用DB全テーブルのハッシュが実行前と一致することを確認した。
- frontend lint、backend lint/compile、対象E2EのTypeScript検査、Webビルド成功。
  Webの既存500kBチャンク警告は継続。追加の有料画像生成は0回。
- 過去の凍結プロンプトとの比較は、今回の変更前から存在した商品参照文の
  `matching asset` → `matching productId (assetId for legacy references)` の差で不一致。
  凍結成果物を改ざんせず、その比較が成功したとは扱わない。
- 通常APIを再起動し、`full_frame_v2` の応答スキーマとWeb稼働、既存履歴の再生成案内を確認。
  通常EC 11テーブル・Canvas 5テーブルのハッシュが実行前後で一致し、庭・既存履歴は不変。
  添付スクリーンショットと保存済みPNGを照合した。開いているChromeへの直接接続は使えず、
  保存履歴の実画面検証は別のChromiumで実施した。
