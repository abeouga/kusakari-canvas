# 買い物リストの必要数（shoppingTargets）

## Context

issue #40 で、庭編集画面の買い物リストの各カードに「配置数/必要数」（例 `2/3`）を表示することになった。
それまでの買い物リストの数量は庭に置いた数そのもので、ECの `garden_shopping_items` も商品IDと名前だけを保存しており、配置数と別の「必要数」はどこにも存在しなかった。

## Decision

- 必要数はCanvasの庭（GardenDocument）に `shoppingTargets: [{ key, quantity }]` として保存する。
  - `key` は買い物リスト行のキー（`product:<商品ID>` または `asset:<アセットID>`）、`quantity` は1〜999の整数。最大200件、キーは重複不可。
  - 未指定の行の必要数は配置数（ECで追加した未配置商品は1）。利用者が買い物リストのカードの −/＋ で変えた行だけを保存する。
  - 変更時は、その時点の買い物リストに出ていない行の値を捨てる。
- MySQLでは `gardens.shopping_targets_json`（LONGTEXT、NULL可）に保存する。Alembic `0008` で列を追加するだけで、既存の庭は NULL＝従来どおり（必要数＝配置数）になる。
- 保存は従来どおり庭全体のPUT（revision比較）に含める。庭の複製では必要数も複製する。
- ECへ渡す買い物リストの数量（`/gardens/{id}/shopping-list`）とカート投入数は、今回は変えず配置数のままとする。

## Alternatives

- ECの `garden_shopping_items` に数量列を追加し、ECを正本にする：EC側のスキーマ・API・画面の変更が別リポジトリで必要になり、このissueだけでは完結しないため見送った。
- 既存データだけで `max(配置数, EC追加済みなら1)` を必要数として表示する：データ変更は不要だが `2/2` か `0/1` しか表せず、issueの `2/3` を表現できない。

## Consequences

- 配置数は常に `objects` から数え、必要数だけを保存するため、配置・削除で配置数は自動で変わり、必要数は再読み込み後も維持される。
- 必要数を指定した行は、その後に配置を増減しても必要数が追従しない（指定値が優先される）。
- 0007までのCanvasは0008のDBを未知の版として起動を止める。リリースや並行開発では、0008のDBを使う前にこの変更を取り込む。
- ECの買い物リスト・カート投入を必要数ベースにする場合は、EC側と合わせた別の変更として扱う。
