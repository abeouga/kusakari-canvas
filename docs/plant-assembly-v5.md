# 植物モデル構成規則 v5（茎・枝・葉の調整と種類の追加）

v1〜v4 の経緯は [modular-plant-models.md](modular-plant-models.md)、[plant-library-v2.md](plant-library-v2.md)、[plant-naturalness-v4.md](plant-naturalness-v4.md) を参照。Issue: abeouga/kusakari-canvas#35

## Context

出品者が入力した植物特徴から作る 3D モデルについて、次の不満があった。

- 茎・幹の曲がり、先端への細まり、幹の本数を指定できない。
- 枝は全体で 1 つの `branchCount` と `branchAngle` だけで、枝の角度は樹木・針葉樹・株立ちでしか表示されない。分岐の段数や垂れ下がりは規則の中で固定されていた。
- 葉の大きさは 1 つの値だけで、ばらつきや先端との差、葉の付き方を表現できない。密度は 3 段階だけだった。
- 品種別の形は 5 種だけで、AI 推定でしか設定できなかった。

保守面では、版ごとの生成コードが互いに import し合っていた（v4 が v3 を、v3 が v1 の補助関数を使う）。そのため改善を入れると旧版の出力が変わる危険があった。

庭の保存時、サーバーは保存された構成を特徴から作り直し、一致するかで改ざんを検出している（`validation.py`）。旧版で作られた商品や庭を保存し続けるには、旧版の生成処理が残っている必要がある。

## Decision

- v1〜v4 の生成コードを `backend/kusakari_canvas_api/plant_legacy/` に移して凍結する。用途は保存済み構成の検証だけで、今後は編集しない。移動前後で v1〜v4 の 76 通りの出力が一致することを、JSON の SHA-256 で確認した。
- 新しい規則 v5 は `backend/kusakari_canvas_api/plants/` に置く。`plant_legacy` は import しない。
  - `schemas.py`: プロフィールと構成の定義
  - `species.py`: 植物タイプと種類の表（データ）
  - `geometry.py`: 配置計算と部品リスト
  - `growth.py`: 樹木系・草花系・グラス・ロゼット・ヤシの 5 つの成長処理
  - `assembly.py`: 外形合わせ
- 種類は表の行で定義する。成長処理は種類の特徴フラグ（葉柄、上向きの葉、花茎など）だけを参照する。種類を追加するときは成長関数ではなく行を増やす。
- v5 は既存のカタログ v4 の GLB を再利用する（`version: 5`、`catalogVersion: 4`）。部品 GLB とカタログ v4 は変更しない。
- 追加した入力項目は次のとおり。`null` は「自動」を意味し、植物タイプと種類の値を使う。追加項目のない既存プロフィールも、そのまま v5 で組み立てられる。
  - 茎: `stemCount`, `stemCurve`, `stemTaper`
  - 枝: `twigLength`, `branchLevels`, `branchDroop`, `branchStart`
  - 葉: `leafSizeVariation`, `leafTipRatio`, `leafArrangement`
- 枝全体の届く範囲は「植物の幅」で決まる（外形合わせで常に指定幅に収めるため）。そのため枝の長さは独立項目にせず、親枝に対する小枝の長さ `twigLength` とした。
- `leafDensity` を 5 段階（sparse/low/medium/high/dense）にした。樹木系の葉の枚数は、樹冠の表面積を葉の面積で割った値に密度を掛けて決める。計算にはプロフィールの指定寸法を使うので、外形合わせの途中で部品数は変わらない。
- `leafSizeCm` の範囲を 0.5〜200cm に広げた（v1〜v4 は 2〜80cm）。ロゼットで選べる葉にハート形と丸葉を加えた。
- 種類は既存 5 種（イロハモミジ、モンステラ、イベリス、フウチソウ、ゴールドクレスト）に、オリーブ、ラベンダー、バラ、アジサイ、ツゲ、ギボウシを加えた 11 種。
- `POST /api/model-assemblies/resolve` は常に v5 を返す。`?version=` は廃止した（呼んでいたのは検証スクリプトと E2E だけ）。保存済み構成の読み込みでは、`version` が 5 なら v5、それ以外は v1〜v4 として判別する（v1 は `version` 欄を持たない）。
- EC は `PlantModelProfile` に同じ項目を持つ。`null` の項目は JSON に出さないため、既存の保存プロフィールと API 応答の形は変わらない。出品フォームは種類の選択と、各項目の「自動 / 指定」を持つ。

## Alternatives

- **破壊的変更とデータ変換**: 商品と庭の構成をすべて v5 に作り直す方法。会員の庭の形が本人の操作なしに変わり、EC と Canvas の 2 つの MySQL を 1 つのトランザクションで変換できないため採用しない。
- **旧版の生成コードを削除し、保存構成の検証を形式チェックに変える**: コードは減る。ただし旧版の構成をクライアントが任意に書き換えられるようになり、改ざん検出が弱まるため採用しない。
- **v5 用に部品カタログ v5 を作る**: 既存の部品で今回の改善はすべて表現できた。同じ GLB を複製するだけになるため、今回は作らない。

## Consequences

- 新しい改善は `plants/` だけで行えばよく、旧版の出力を壊す心配がない。`plant_legacy/` は残るが編集対象ではない。
- 種類の組み合わせ（植物タイプ・葉の形・選べる花の形）は、Canvas の `species.py` と EC の `frontend/src/plantSpecies.js` の両方にある。不一致は Canvas が 400 で拒否する。
- 1 構成あたり 1500 部品の上限は変えていない。高さ 2m を超える広葉樹に 7cm 程度の実寸の葉を付けると、樹冠が透けて見える。小さな葉が密な低木（ツゲなど）も同じ。葉の房をまとめた部品 GLB（カタログ v5）が今後の改善候補。

## Verification

- 独立検証（E2E では足りない部分）: `plant_legacy` への移動で v1〜v4 の出力が変わる失敗を検出するため、移動前後で 76 通りの構成 JSON を SHA-256 で比較した（全一致）。E2E で使うのは v1〜v4 の代表 4 構成だけなので、これだけでは版や形態の網羅が不足する。
- E2E（実 API / MySQL、実 Cognito）: `npm run test:e2e -- e2e/plant-v5-controls.spec.ts` で次を確認する。成果物は `artifacts/e2e/plant-v5/` に保存する。
  - 種類の選択と、茎・枝・葉の項目の調整
  - プレビュー、商品保存、再編集時の値の表示
  - 同じ特徴から同じ構成が返ること、調整項目で部品が変わること
  - 庭へのドラッグ配置、自動保存、再読み込み
- 旧版互換: `e2e/plant-v3.spec.ts` で、v1〜v4 の保存構成（`e2e/fixtures/plant-composition-v{1..4}.json`、v2〜v4 は凍結した旧版コードで生成）を含む庭が保存・再読み込みでき、改ざんが 400 になることを確認する。
