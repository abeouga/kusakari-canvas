# ECのCognitoログインとの共用

他PCでの利用は[認証セットアップ手順](cognito-setup.md)を参照してください。DBの資格情報は共有せず、公開接続設定だけをGit管理します。

## Context

Canvasは従来、dev/e2e/containerごとの固定所有者を使っていました。利用者認証はECで行い、認証済み利用者の庭を扱います。

## Decision

`KUSAKARI_AUTH_MODE=cognito`で有効化します。`KUSAKARI_CANVAS_AUTH_EC_URL`には信頼するEC APIオリジンを指定します。
CookieのセッションをECへ照会し、返された会員IDを所有者とします。庭・写真・履歴・サムネイル・買い物リスト・AI生成の全経路に適用します。
更新系のCSRFもECで検証します。未ログイン401、確認情報/権限不足403、認証先障害503で拒否します。
署名のない利用者ヘッダーやクライアントownerIdを信用しません。ECとの認証確認に失敗してもデモ所有者へ切り替えません。
既存庭の所有者をテスト利用者へ自動で書き換えません。認証なしのデモは従来の制限下で維持します。

## Alternatives / Consequences

Canvas専用ログインを作らず、ECのセッションを共有します。EC停止中は認証済み操作も停止します。
未ログインでCanvasを開くと、ECの`/account/login?returnTo=元のCanvasのURL`へ自動転送します。Canvas内にはログインフォーム/ログインボタンを設けません。ログイン成功後は元のCanvas画面へ戻ります。編集中のCanvas/EC APIが401を返した場合も同じEC画面へ転送します。403や認証先障害503では自動転送せず、エラーを表示します。
設定とテストアカウント作成手順は隣接`kusakari-terraform/README.md`、認証境界の全体仕様はECの`docs/cognito-auth.md`を参照します。
2026-10-19に東京の実User Pool `ap-northeast-1_HvkWp5qwE`を作成し、成功系を検証しました。Git対象外`.env`にCognitoモードとEC APIオリジンを設定済みです。
