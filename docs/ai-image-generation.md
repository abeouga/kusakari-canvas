### Context

### Decision

- 撮影時の GardenDocument に保存された `productId` から登録画像を自動取得する。
  店舗・商品の再選択は不要。同じ商品の複数配置は1参照、別商品は同じアセットでも別参照とする。
- Canvasの `POST /api/ai/product-references` からECの `POST /api/products/references` を呼び、
  ID・商品名・画像URL・販売状態・植物モデル有無だけを取得する。大きな3D構成JSONは転送しない。
- 既存庭の参照を壊さないため、ID指定の画像メタデータは販売終了後も読み取り可能とする。
  販売一覧・購入判定は変更しない。存在しない商品を類似商品で代用せず、再配置を案内する。
- 生成サーバーで撮影時の `(assetId, productId)` と参照商品の一致・重複を検証する。
  同じ商品IDを配置一覧・画像役割・履歴まで持ち、異なる商品画像を混同しない。
- 登録画像は従来と同じ形式・寸法・容量制限を適用する。固定EC画像origin内の
  `/images/` の下位フォルダーも許可するが、外部origin・パストラバーサル・リダイレクトは禁止する。
  未対応画像の追加写真入力は残す。取得失敗時は生成を止め、明示的な再取得を提供する。
- 利用者が例外を取り下げた旧「木」`canvas-oak` は新規の商品・配置一覧から除外する。
  保存済みの庭を壊さないため `tree_oak` のアセットとGLBは保持する。
  商品未紐付けの旧配置は新UIで商品選択の例外処理を設けず、商品一覧からの再配置を案内する。

## 新フェーズ1：詳細設計（2026-10-14確定）

本節は新フェーズ2〜5の実装仕様です。指定された担当はAstra / highです。この段階での成果は設計とコード上の依存確認であり、実APIの生成品質を確認した結果ではありません。

### Context：コードで確認した変更上の注意点

1. `ai_service.generate_image` は生成後に自動で `history_service.save_history` を呼びます。方式情報の追加を新3まで遅らせると、新2で作った全画像採用の結果を旧方式と誤記録するため、保存契約を新2へ前倒しします。
2. `history_service.validate_history` はDTO全体から保存内容のSHA-256を作ります。新フィールドを無条件にハッシュへ加えると、旧履歴の同一内容再保存が409になるため、旧方式のハッシュ形式を保持します。
3. `migrations.validate_schema` は履歴テーブルが存在する版を `revision == HEAD` で判定しています。HEADだけを0004へ変えると、正しい0003 DBを拒否するため、0003／0004それぞれの構造を明示します。
4. API応答のデコードは入力用8MB制限を使い、履歴Afterは20MBまで受け付けています。全画像採用に合わせ、生成応答から履歴まで出力用20MBへ統一します。入力画像は引き続き8MBです。
5. 現在の比較スライダーは保存PNGを加工せず、CSSでBeforeの表示範囲だけを切り替えています。これはAfterを作る貼り戻しとは異なる表示処理です。

### Decision A：確定した画像処理契約

| 項目 | 契約 |
| --- | --- |
| 主画像 | 撮影時点の庭写真＋全3D配置。同じ `GardenDocument` のスナップショットに対応する不透明PNG |
| 補助画像 | 同じ庭写真・寸法・座標で、対象の植物が見える表示状態にした画像。主画像の個数・位置・前後関係を優先する |
| 参考写真 | アセットごとに選んだ植物の葉・樹皮・色の参照。背景・文字・成熟木の寸法を転写しない |
| 入力順 | 主画像1枚、補助画像、参考写真の順。既存のID対応付けと合計16枚上限を維持する |
| coverage | クライアントから引き続き送る。API用マスクの作成と評価の分類に使い、生成後の画素選択には使わない |
| APIマスク | 新2の標準は現行の8px余白・家具除外。画像配列には入れず、第一画像に適用するマスク引数へ渡す |
| 寸法調整 | 現行の `padded_size` と `pad_image` を使い、右・下にだけ余白を追加する。写真を引き伸ばさない |
| 最終After | 応答の左上 `(0, 0)` から元写真の幅・高さを切り出した全画像。色補正・再配置・局所合成を行わない |

`composite_result` を削除し、`ai_images.py` に `finalize_generated_image(content, original_size, expected_size) -> str` を置きます。引数は生成PNGのbytesと2組の寸法だけです。Beforeの画素・coverage・編集マスクを受け取らないため、この関数で元画像へ貼り戻す経路を持ちません。

関数は、不透明PNGと容量の検査、要求したAPI寸法との完全一致、元寸法が応答内に収まることの検査、固定座標の余白除去、PNG出力の順に処理します。`decode_image` の出力側呼び出しには `MAX_AFTER_IMAGE_BYTES` を明示し、再エンコード後も20,000,000bytes以下を検査します。元寸法と応答寸法が同じ場合も、許容される画素変更は0です。

APIの元PNGとAfterは再エンコードでファイルbytesが変わる可能性があります。保証するのは「デコードした応答の写真範囲とAfterのRGBA画素の完全一致」です。一度決定したAfterのPNGは、レスポンス・履歴・ダウンロードで同じbytesを使用します。

`AI_OUTPUT_INVALID`、`AI_OUTPUT_DIMENSION_MISMATCH`、`AI_OUTPUT_TRANSPARENT` の502は維持します。出力容量超過は502 `AI_OUTPUT_TOO_LARGE` として区別し、画像を切り貼りして救済せずエラーを返します。自動再試行は追加しません。履歴保存だけの失敗は従来どおり画像を返し、`historySaved=false` とします。

出力用上限は `ai_provider.py` のBase64長／デコードbytes、上記関数、履歴検証で共通化します。リクエスト全体48MBの上限は維持します。庭写真には既存の5MB制限があり、Before8MB＋After20MB＋写真5MBのBase64は約44MBです。別途JSON全体の48MB制限も適用され、巨大な配置データまで無条件に保存可能とは扱いません。

### Decision B：指示文とAPIマスク

既存の `generation_prompt` を `ai_prompt.py` へ移し、主画像の役割、変更する植物、維持する構図と家具、補助と参考の役割、自然な葉先と接地、追加余白の扱いの順に組みます。通常の文字列連結とラベル配列を使い、テンプレートエンジンを導入しません。

「マスク外の全画素を同一にする」「影をマスク内だけに閉じ込める」という指示は外します。背景の構造・既存物の位置・カメラの視点を保持し、植物の周囲は自然な葉先・地面・弱い接地影を許す指示へ変更します。固定8pxが依然として生成を制限する可能性は、新4の評価事項として残します。

マスクなしの比較が必要になった時点で、`edit_images` の `mask` を `bytes | None` にします。`None` のときはSDK引数そのものを省略し、指示文のマスク説明も省略します。比較切替はE2E専用設定とし、ブラウザーの生成要求へモード選択を追加しません。新2で将来用の未使用設定を作る必要はありません。

マスクなしの比較では、マスク説明の有無以外の指示、画像bytesと順番、モデル・品質・寸法を揃えます。各1回では出力のばらつきを排除できないため、参考比較として判定します。旧方式の結果と新方式の結果は指示文も異なり、貼り戻しだけの効果を分離した実験とは扱いません。

マスクを省略する場合も、可視植物がない入力を課金前に拒否する検査は残します。coverageはこの検査と評価にも使うため、不要になったマスク送信処理だけを削除し、遮蔽判定・撮影の共用コードを一括削除しません。

[OpenAI公式仕様](https://developers.openai.com/api/docs/guides/image-generation)では、GPT Imageのマスクは指示による編集ガイドであり、厳密な輪郭一致を保証しません。[APIリファレンス](https://developers.openai.com/api/reference/python/resources/images/methods/edit)でもマスク引数は任意です。新方式の構図保持を保証する代替機構としては扱いません。

### Decision C：DTO・履歴・互換性

新フィールド名はAPIで `generationMethod`、DBで `generation_method` とします。型は `ai_schemas.py` の `GenerationMethod = Literal["masked_composite_v1", "full_frame_v1"]` とし、履歴DTOも同じ型を参照します。値は出力の作り方を表し、開発モデル、画像生成モデル、APIマスクの有無とは独立です。

| 対象 | 変更 |
| --- | --- |
| `AiImageRequest` | 方式の入力を追加しない。既存の主画像・補助・参考・coverageを継続する |
| `AiImageResponse` | 必須の `generationMethod` を追加。新しい生成ではサーバーが `full_frame_v1` を設定する |
| `HistorySaveRequest` | 必須の `generationMethod` を追加。自動保存と再保存で応答と同じ値を渡す。欠落・未知値・nullは400 |
| `HistorySummary` / `HistoryDetail` | 保存済み方式を返す。詳細はSummaryの継承を利用する |
| `HistoryEntity` | `generation_method` を `VARCHAR(32) NOT NULL` として追加する |
| `AiImageGeneration.generate` | `savePayload.generationMethod = generated.generationMethod` を新2で追加し、再保存で値を維持する |
| `GenerationHistory` | 新3で方式の説明を詳細欄へ表示する。旧履歴のAfterは再計算しない |

方式の欠落を新旧どちらかへ推測して補いません。保存済み旧履歴の閲覧互換と、更新前から開いている旧タブの要求互換は別です。旧タブの方式なし再保存は400で拒否し、そのタブに残るAfterのPNG保存は利用できます。更新は生成・未保存結果を処理した後に行い、新コードでは再保存payloadを生成処理と同時に更新します。

保存内容のハッシュは `history_service.py` 内の名前付き関数 `history_fingerprint(request, before_png, after_png)` へ分けます。メタデータのJSON化、キー順、画像長と画像bytesの連結順は現行と同じです。

- `masked_composite_v1` の場合だけ、メタデータから `generationMethod` を除外して旧ハッシュ形式を保ちます。
- `full_frame_v1` は方式を含めたハッシュにします。
- 同一IDの保存は、既存行の方式とハッシュの両方が一致する場合だけ成功とします。画像・スナップショット・参照・方式が異なれば409です。
- 移行時に旧PNG・旧スナップショット・旧 `payload_sha256` を書き換えません。旧履歴の明示的な旧方式付き再保存は、従来のハッシュで冪等に成功させます。

この項目はアプリ内の方式識別であり、利用者が提出した再保存画像の生成元を暗号学的に証明するものではありません。既存の所有者・庭・画像・参照検証は継続します。

### Decision D：DB移行

新2でAlembic `0004_history_generation_method.py` を追加し、`down_revision="0003"` とします。旧版の移行ファイルは変更しません。

1. `generation_method` をNOT NULL、一時的なserver default `masked_composite_v1` 付きで追加し、既存行を旧方式として埋めます。
2. defaultを外し、以降は保存コードで方式を必ず指定します。旧アプリの書込みを新方式と誤認する余地を作りません。
3. `migrations.py` のHEADを0004、対応版を0001／0002／0003／0004にします。履歴テーブルは0003以降に存在し、方式列は0004だけに存在する条件へ変えます。
4. 現行のバックアップとスキーマ確認を通して移行します。方式列以外の旧列の値・画像bytes・件数・IDを保持します。自動downgradeで履歴情報を消しません。

`verify_migrations.py` に、実際の0003スキーマへ旧形式の非空履歴を入れて0004へ移すケースを追加します。新モデルで旧スキーマへINSERTせず、旧列を明示したfixtureを使います。既存データ比較は旧列の集合で行い、新列の追加による当然のハッシュ差で旧データの破損を見落とさないようにします。追加列の値は別に検査します。

### Decision F：品質の判定方法と許容値

以下は本プロジェクトが採用する初期の判定基準です。公式APIの精度保証でも、既に達成した測定値でもありません。評価後に都合よく閾値を緩めて同じ結果を合格にしません。変更時は理由と基準の版を記録して再評価します。

固定入力のBefore上で、生成前に静止物の目印5点と、測定可能な各植物の根元・樹冠中心・主要な外形を記録します。画像の短辺を `S` とし、数値比較は原寸で行います。生成画像を移動・拡縮・透視補正してから比較することはしません。

| 評価項目 | 許容条件・判定方法 |
| --- | --- |
| 出力の忠実性 | Afterと未加工API応答の写真範囲のRGBA不一致0画素。原寸一致、透過0画素 |
| 画角・構図 | 建物の角・固定物などの目印の移動量が各点 `max(3px, Sの0.5%)` 以下。画面内に分散した3点以上で測定できなければ判定不能 |
| 植物の位置 | 測定可能な根元と樹冠中心の移動量がそれぞれ `max(3px, Sの1%)` 以下 |
| 見かけの大きさ | 全体が見える植物の主要外形の幅・高さがBeforeから各±10%以内。葉先の小さな凹凸は許す。遮蔽で全体が見えない個体は全体寸法を推定採点しない |
| 個数・参照対応 | 主画像で識別できる植物の増減なし。樹木／低木や葉・樹皮の参考の取り違えなし。品種・実寸・実商品同一性は保証対象にしない |
| 前後関係 | 手前の家具へ奥の葉が突き抜けない。完全に隠れた植物を勝手に露出させない。完全遮蔽個体の外観は判定不能 |
| 背景と家具 | 建物・家具の消失、追加、部材数や形の変化がない。色や質感の微小な差は目視評価し、変更画素数だけでは落とさない |
| 自然さ | 原寸表示で樹冠の直線的切断、平底の切り抜き、旧3D輪郭、根元の浮き、目立つ継ぎ目、光の方向の矛盾がない |

1280×853pxの既存サンプルでは、構図の目印は約4.3px、根元／樹冠中心は約8.5pxが初期許容値です。測定値と目視判定を両方残します。目印や根元が見えない箇所は判定不能と明記し、見えないことを保持成功の証拠にしません。

3ケースそれぞれについて、測定可能な必須項目が範囲内で、自然さに「要修正」「破綻」がない場合に、その評価条件で許容とします。測定可能な必須項目の判定不能は未完了です。撮影前から定義した完全遮蔽の外観などは対象外とし、対象外の範囲を報告します。少数ケースの許容を一般的な成功率へ読み替えません。

### Decision G：検証と証拠

新2では `verify_ai_images` を、余白内外に異なる色・座標パターンを持つ制御PNGによる「写真範囲の全画素保持」の検証へ変更します。背景や家具を別途元画像で上書きした実装なら失敗する条件にします。誤寸法・透過・壊れたPNG・容量超過・切出し範囲不正も確認します。実APIにこれらの異常出力を確実に返させられないため、独立した画像処理検証を使います。

実MySQLの履歴確認には、新旧方式の保存・一覧・詳細、同一ID同一内容の再保存、方式だけ変更した409、未知方式と欠落の400を含めます。0003の旧ハッシュが移行後も再保存に使えることを実際の旧fixtureで確認します。方式以外のモデル・品質・参照・所有者の検証を弱めません。

新4のE2E証拠出力は `AiSettings` に任意の `evidence_directory` を追加し、`from_profile("e2e")` かつ既存の実生成フラグ2つと `KUSAKARI_CANVAS_AI_EVIDENCE_DIR` が指定された時だけ有効にします。通常プロファイルでは有効にしません。利用者のリクエストから保存先やモードを受け取りません。

`ai_evidence.py` の単一の保存関数が、専用実行フォルダーの生成ID別サブフォルダーへ `provider.png`、`after.png`、実際の `prompt.txt`、送信マスク、寸法・方式・モデル・入力順・入力ハッシュのメタデータを保存します。公開サンプル専用E2Eの主画像・補助・参考・snapshotは既存harnessが保存します。過去フォルダーを上書きしません。APIキー・認証ヘッダー・SDK応答全体は記録しません。

証拠保存のI/O失敗で正常生成結果を失わせず、評価側が必須ファイルの不足を検出して未完了にします。大きいPOSTの応答本文をChromiumのinspect cacheから読む方法は再採用せず、HTTP状態・表示中After・実履歴GETで結果を照合します。API未加工出力との画素比較は証拠PNG同士で行います。

新2／新3では無課金の入力・履歴・移行検証を先に行います。実生成は新4で品質のsingle／multiple／overlap各1回を正常系統合確認と兼用し、保存障害からの復旧確認に別の1回を使います。基準は計4回です。マスクなし比較が必要なら代表ケースで1回追加し、原因のない再試行を繰り返しません。保存障害確認は専用MySQLへの明示した障害注入を使い、再保存中のAPI生成回数は0を要求します。

各実装段階の変更対象に対し `npm run lint`、`npm run lint:api`、`npm run compile:api`、`npx tsc --noEmit -p e2e/tsconfig.json`、`npm run build:web` と関連E2Eを実施します。課金フラグは通常E2Eへ混ぜません。新2／新3の実生成・復旧は新4まで未確認と報告します。

### Alternatives / Consequences

生成方式をAPI入力から自由に選択させる方法、保存日時から新旧方式を推測する方法、旧画像を再生成して揃える方法は採用しません。明示した方式列により、同じ庭の履歴で新旧画像を正しく解釈できます。代わりに新2でDTO・移行・再保存payloadをまとめて変更する必要があります。

新方式でも、写真に写った塀・既存植栽の奥行きを自動で正しく理解する保証はありません。品質不良は後処理で隠さず、入力・指示・APIマスクの設計へ戻して改善します。

## Context

フェーズ1のBeforeとフェーズ2の補助画像を、植物の商品参照画像とともに画像編集APIへ渡します。庭写真の画角・出力寸法と、変更対象外の画素を保持する必要があります。ECが商品情報の正本であり、庭・写真・配置はCanvasが扱います。

## Decision

- 開発モデルはAstra / high（描画・設計・レビュー）と6.1sol / high（バックエンド・UI）です。画像生成モデルは別に`gpt-image-2.5-sunburst`、品質`medium`を固定しています。
- `POST /api/gardens/{id}/ai-image`を追加しました。ブラウザーからOpenAIへ直接接続せず、バックエンドがImages Edits APIへ送信します。
- 最初の画像は庭写真と全配置を重ねたBeforeです。その後に対象別の補助画像、素材ごとに選んだ商品参照画像を並べ、プロンプトで用途・対象を明記します。3D単体の切り抜き見本は送信しません。
- `GET /api/ai/status`で設定状態、`GET /api/ai/stores`で店舗、`GET /api/ai/candidates`で素材に対応するECの商品候補を取得します。生成用の店舗・商品選択によってECカートを変更しません。
- 撮影時にGardenDocument・アセット・店舗を複製します。生成にはそのスナップショットと撮影画像を使用します。未保存の編集を許可し、所有庭・庭ID・revision・配置・アセットをサーバーで検証します。
- 植物アセットごとに商品を明示選択します。同じアセットが複数配置されている場合、参照画像はそのアセットに1枚です。商品IDの所属はECの素材候補APIで再照合します。
- 入力画像はBefore・補助・参照の合計16枚以内です。超過時はエラーを表示し、自動的に画像を省略しません。編集領域の処理用画像とAPIのマスクはこの枚数に含めません。

### 商品画像の扱い

現行のCanvas対応デモ商品にはSVGの参考図が登録されています。ECの別のPNG画像にもAI生成デモ画像があり、実在商品の写真であるとは扱いません。

商品登録画像が対応するPNG/JPEG/WebPで、固定EC originの許可された`/images/`配下にある場合、サーバーが取得します。SVGや許可外URLの場合は、選択商品に対して利用者が参考写真を追加します。追加写真は商品登録画像の正本とは区別して結果に記録します。参照なしの生成やSVGの無言の代用は行いません。

ECからの取得はリダイレクト禁止、タイムアウト・応答容量制限付きです。クライアント指定の任意URLをサーバーで取得しません。

### 編集範囲と画角

撮影時に、可視の植物を赤、可視の非植物配置を緑、背景を黒とする処理用PNGを取得します。葉の切り抜き・深度関係を保持します。この画像はOpenAIの参照画像配列には入りません。

サーバーは赤信号が2より大きい画素を植物領域、緑信号が2より大きい画素を保護対象とします。植物領域を半径8px相当の正方形で広げ、非植物領域を除いた範囲を編集領域にします。APIマスクの透明部分が編集対象です。

原画像の座標を維持し、右・下だけに余白を追加します。各辺を16の倍数・最低1024pxへ揃え、長辺2048px・3,686,400画素以内に制限します。原画像の拡大縮小は行いません。上限超過時はエラーにします。応答寸法が要求と異なる場合は結果を採用しません。

生成画像から余白を除き、編集領域の内側だけをBeforeへ貼り戻します。編集領域外と家具の保護領域はBeforeの画素を保持します。元写真に写った壁・既存樹木などの奥行きを解析した保証ではありません。

## 検証方針

通常のE2Eは実EC API、Canvas API、専用MySQL、Chromiumを使い、課金を伴う画像生成を行いません。合成写真と専用庭で商品選択、追加写真検査、入力スナップショット、処理用領域の向きと色、キー未設定エラー、描画例外後の復元を確認します。

実生成E2Eは別ファイルに分け、明示的な有効化と専用設定があるときだけ1回生成します。出力の編集範囲外・家具の画素差、元寸法、二重送信防止、PNG保存、再読み込み後の庭JSONを確認します。実利用者の写真は検証成果物へ保存しません。

画像処理の独立検証では、背景全体を書き換えた制御画像や誤った出力寸法を入力し、貼り戻しと出力拒否を確認します。実APIに誤寸法・透過結果を確実に返させることはできないため、この異常系は画像処理関数を直接検証します。OpenAI正常応答のモックでE2Eを代替するものではありません。
