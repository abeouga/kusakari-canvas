# 写真のカメラ校正

## Context

庭の輪郭の外接矩形を画面へ対応させるだけでは、撮影カメラも高さ方向の投影も定まらない。画面上で木を垂直にする従来の近似では、遠近による大きさを再現できなかった。

当初は、水平な地面にある実寸の分かる長方形を写真上で指定し、その実寸からカメラを求める画面（「写真のカメラを設定」）を用意した。しかしこの画面は用途が分かりにくく、使われなかった。輪郭の各辺の実寸からもカメラを求められる（[写真上の辺の計測](polygon-edge-editing.md)）。さらに、画面を開いている間の状態が、自動保存・離脱の確認・辺の入力・配置などの条件に入り込み、編集画面を複雑にしていた。

## Decision

写真の撮影カメラは `GardenDocument.photo.calibration` に保存し、写真上の3D表示、写真のクリック位置、グリッド、面積・外周、配置範囲の検証に使う。新しいカメラは、輪郭と全辺の実寸から求める（`method: 'edges'`。[写真上の辺の計測](polygon-edge-editing.md)）。

基準長方形からカメラを求める画面と、そのための `POST /api/photo-calibration` は取り除いた。基準長方形のカメラ（`method: 'rectangle'`、既定値のため保存時は省略）は、その画面で保存された庭を開く・表示する・保存するためだけに残す。今の画面から新しく作る操作はない。全辺の実寸を入れると、今のカメラを開始値にして、辺から求めたカメラに置き換わる。

### 基準長方形のカメラ（既存の庭の互換）

- 水平な地面にある長方形の四隅（手前左→手前右→奥右→奥左の順の正規化座標）、その幅・奥行き（m）、任意で手動の焦点距離（画素単位）から求めたカメラである。長方形の中心が庭の原点、手前側が＋Zとなる。基準長方形は庭の輪郭とは別の情報である。
- PUTのたびに、保存された基準点・基準寸法と、手動の場合はその焦点距離から姿勢を計算し直し、クライアントの行列をそのまま信用しない。
- 画像中心を主点、正方画素、レンズ歪みなしと仮定する。焦点距離が推定の場合は、実寸平面のホモグラフィの直交条件・等長条件から推定する。
- OpenCVの `solvePnPGeneric / SOLVEPNP_IPPE` と `solvePnPRefineLM` で複数の姿勢候補を検討し、カメラが地面より上、基準点が前方にある候補を残す。再投影誤差が許容範囲を超えた場合は拒否する。
- 交差・退化した基準点、自動推定できない画角、対応範囲外の画角（縦15〜110度）は400 `INVALID_CALIBRATION` で拒否する。
- 「輪郭と寸法」の帯のパースの状態は「基準長方形から推定」、面積・外周の注記は「写真の基準長方形の実寸から求めたパースに基づく推定」と表示する。

### 描画

- 校正済みの写真は、Three.jsの通常の `PerspectiveCamera` に位置・姿勢・画角を設定する。地面と全GLBで同じカメラを使用し、モデル別の遠近補正は行わない。撮影姿勢に応じた画面上の傾きはそのまま再現する。
- 写真クリックには同じカメラのRaycasterを使用する。輪郭の地面座標は同じ姿勢からのレイとY=0の交点とし、グリッドも同じカメラで投影する。
- 地平線を越える輪郭、庭の実寸範囲を超える輪郭は保存できない。境界の入力誤差には5cmの許容幅を持たせる。

### 永続化

`GardenDocument.photo.calibration` にversion、求め方（`edges` のときだけ `method` を持つ）、焦点距離、推定／手動の区分、回転9値、並進3値、再投影誤差を保存する。基準長方形のカメラは四隅と基準寸法も持ち、辺から求めたカメラは持たない。回転・並進は世界座標からOpenCVカメラ座標（右・下・前）への変換である。

Three.jsオブジェクトは保存しない。既存のphoto_json列を使うためDBマイグレーションは不要。revisionによるスナップショット保存を維持する。

校正データのない写真は従来の表示で開き、「カメラ未設定・土台寸法からの概算」を明示する。全辺の実寸を入れた時点で透視投影へ移行する。旧 `photo.corners` は互換用であり、校正後のカメラ姿勢には使わない。輪郭の描き直しで校正を消さない。

## Alternatives

- 任意輪郭の外接矩形：実寸の点対応・高さ方向の情報が不足する。
- ARKit等で撮影時に姿勢取得：既存写真では利用できず、別の撮影アプリと端末対応が必要。
- 外部のカメラ合わせソフト：操作・座標系・保存情報の受け渡しが増える。
- 手動姿勢スライダーのみ：見た目は合わせられるが、複数点との整合を保証しにくい。
- 基準長方形の画面を残す：用途が分かりにくく使われず、画面を開いている間の状態が編集画面の条件を複雑にしていた。辺の実寸からカメラを求められるため取り除いた。
- 基準長方形のカメラのデータの扱いも消す：その画面で保存した庭が保存できなくなるか、カメラが外れて配置物の写真上の位置が変わるため採用しない。
- カメラを計算するAPIを残す：画面からもECからも呼ばれないため取り除いた。保存時の計算し直しはサーバー内部で行う。

## Consequences

基準長方形のカメラを持つ庭の基準点・基準寸法・画角は、画面から変更できない。パースを直したいときは、全辺の実寸を入れて辺から求めたカメラに置き換える。

基準長方形のカメラは、実際に長方形である基準と正しい実寸を前提とする。傾斜地、広角レンズの歪み、パノラマ、偏った画像切り抜きによる主点の移動には対応していない。写真内の既存物による遮蔽、照明・影の一致も対象外。残差は基準4点との一致度であり、写真全体の正確さを保証しない。

## 検証

主検証は `e2e/photo-calibration.spec.ts`。

- O：既知のThree.jsカメラで模擬画像を作り、基準長方形のカメラを持つ庭を実API・専用MySQLに用意して画面で開く。カメラ設定の入口がないこと、基準点に使っていない高さ2mの点の投影、手前・中央・奥の見かけの高さ、リサイズ後の写真へのドロップ位置の実寸、保存時の行列の計算し直し、再読み込み後の復元、パースの表示、辺の計測値を確認する。
- P：保存時に、交差した基準点と真上視点の画角の不定性を400で拒否し、手動画角のカメラは計算し直して保存することを確認する。

`artifacts/e2e/photo-calibration-current/` の `camera-calibrated-reloaded.png`、`camera-calibrated.json`、`camera-metrics.json`、`camera-calibrated-measurement.png` に証跡を出力する。実写画像に対する精度は未検証。

参考：[OpenCV solvePnP](https://docs.opencv.org/4.12.0/d5/d1f/calib3d_solvePnP.html)、[fSpyのカメラ合わせ](https://fspy.io/tutorial/)。
