# 写真のカメラ校正

## Context

庭の輪郭の外接矩形を画面へ対応させるだけでは、撮影カメラも高さ方向の投影も定まらない。画面上で木を垂直にする従来の近似では、遠近による大きさを再現できなかった。

## Decision

水平な地面にある実寸の分かる長方形を基準にする。任意多角形の庭輪郭とカメラの基準点は別のデータ・操作とする。

1. 写真を読み込み、庭の輪郭を始点につないで確定する。
2. 「写真のカメラを設定」を開き、長方形の四隅を手前左→手前右→奥右→奥左の順に指定する。
3. その長方形の幅・奥行きの実測値をmで入力する。長方形の中心が庭の原点、手前側が＋Zとなる。基準長方形の寸法は庭の外枠寸法とは独立している。
4. 「カメラを計算」で基準点の残差と高さ1mの確認線を表示する。自動推定できない場合は「画角を手動指定」で縦画角を与える。
5. 「カメラを適用」で反映する。「庭の輪郭も基準長方形に合わせる」は明示的な選択時だけ既存輪郭を置換する。取消では元の設定を維持する。
6. 写真と3D庭の双方で同じオブジェクトを配置・編集し、庭全体の保存でカメラ設定も保存する。

辺をクリックすると、各辺の実寸を入力できる。全辺を入力すると、基準長方形を使わずに輪郭と辺の実寸からカメラを求める（`method: 'edges'`）。ほかの辺の値と写真上の輪郭は変更しない。詳細は[辺の実寸編集](polygon-edge-editing.md)を参照。以下はカメラ設定画面で基準寸法を直接編集する場合の動作である。基準幅・奥行きを変更して再計算・適用しても、写真上の `boundary` と互換用の `corners` はその座標を保つ（明示的な輪郭置換の選択時を除く）。校正の変更に応じて地面の実寸・計測値・投影は更新される。配置物の既存3D座標は保持するため、写真上のモデル位置や見かけの大きさは変わり得る。

### 計算と描画

- `POST /api/photo-calibration` は画像サイズ、正規化した4点、基準長方形の実寸、任意の焦点距離（画素単位）を受け取る。写真自体をこのAPIに送る必要はない。
- 画像中心を主点、正方画素、レンズ歪みなしと仮定する。実寸平面のホモグラフィの直交条件・等長条件から焦点距離を推定する。内部情報を無条件に復元できるとは扱わない。
- OpenCVの `solvePnPGeneric / SOLVEPNP_IPPE` と `solvePnPRefineLM` で複数の姿勢候補を検討し、カメラが地面より上、基準点が前方にある候補を残す。再投影誤差が許容範囲を超えた場合は拒否する。
- 自動推定不能、交差・退化した基準点、対応範囲外の画角（縦15〜110度）は400で返す。
- Three.jsの通常の `PerspectiveCamera` に位置・姿勢・画角を設定する。地面と全GLBで同じカメラを使用し、モデル別の遠近補正は行わない。撮影姿勢に応じた画面上の傾きはそのまま再現する。
- 写真クリックには同じカメラのRaycasterを使用する。輪郭の地面座標は同じ姿勢からのレイとY=0の交点とし、グリッドも同じカメラで投影する。
- 校正中は保存、3D切替、カタログ・プロパティ操作を停止し、未適用の設定を保存済みとは表示しない。
- 地平線を越える輪郭、庭の実寸範囲を超える輪郭は保存できない。カメラ適用後に輪郭を描き直して修正できる。境界の入力誤差には5cmの許容幅を持たせる。

### 永続化

`GardenDocument.photo.calibration` にversion、4点、基準寸法、焦点距離、推定／手動の区分、回転9値、並進3値、再投影誤差を保存する。回転・並進は世界座標からOpenCVカメラ座標（右・下・前）への変換である。

Three.jsオブジェクトは保存しない。PUT時には入力基準点と寸法から姿勢を再計算し、クライアントの行列をそのまま信用しない。既存のphoto_json列を使うためDBマイグレーションは不要。revisionによるスナップショット保存を維持する。

校正データのない旧写真は従来の表示で開き、「カメラ未設定・概算」を明示する。新しいカメラ設定を適用した時点で透視投影へ移行する。旧 `photo.corners` は互換用であり、校正後のカメラ姿勢には使わない。輪郭の描き直しで校正を消さない。

## Alternatives

- 任意輪郭の外接矩形：実寸の点対応・高さ方向の情報が不足する。
- ARKit等で撮影時に姿勢取得：既存写真では利用できず、別の撮影アプリと端末対応が必要。
- 外部のカメラ合わせソフト：操作・座標系・保存情報の受け渡しが増える。
- 手動姿勢スライダーのみ：見た目は合わせられるが、複数点との整合を保証しにくい。

## Consequences

実際に長方形である基準と正しい実寸が必要。傾斜地、広角レンズの歪み、パノラマ、偏った画像切り抜きによる主点の移動には対応していない。EXIF読取りやAR撮影機能は今回の実装範囲外。写真内の既存物による遮蔽、照明・影の一致も対象外。

残差は基準4点との一致度であり、写真全体の正確さを保証しない。特に真上に近い撮影では画角の推定が不安定になるため、分かっている画角を手動指定する。

## 検証

主検証は `e2e/photo-calibration.spec.ts`。既知のThree.jsカメラで模擬画像を作り、実UIで4点を入力、実API・専用MySQLに保存する。基準点に使っていない高さ2mの点の投影、手前・中央・奥の見かけの高さ、リサイズ後の写真クリックの実寸位置、再読込み、取消、保存時の行列再計算を確認する。不正点・真上視点の不定性・手動画角での復帰も実APIで確認する。

校正寸法を10×8mから8×6.4mへ変更・再計算・適用し、写真上の全輪郭座標・corners・配置物・土台寸法が維持され、計測値だけが10mから8mへ更新されることを検証する。再読込み後の計測画面と保存JSONは `artifacts/e2e/camera-calibrated-measurement.png` / `.json` に記録する。

`artifacts/e2e/camera-calibrated-reloaded.png`、`camera-calibrated.json`、`camera-metrics.json` に証跡を出力する。実写画像が未提供のため、実際の庭の写真に対する精度は未検証。

2026-10-02の確認結果：precheck、build:web成功。専用MySQLを使う重点E2E（新規O・P、既存N）3件成功。模擬画像の高さ2mの見かけの長さは手前98.72px、中央92.43px、奥88.02pxとなり、高さ点の投影誤差4px未満、クリック位置の実寸誤差8cm未満を確認した。Chromeにも別の模擬庭を保存・表示した。全E2Eと実写評価は実行していない。
