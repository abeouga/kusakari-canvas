# 庭プロジェクトの複製（UC-08）

## Context

従来の複製はブラウザーが庭を取得し、空の庭を作成し、全体スナップショットを保存する3回のAPI呼び出しでした。
作成後の保存が失敗すると空の複製が一覧に残り、利用者が手で削除する必要がありました。
写真は既定ではMySQLの`gardens.photo_json`にdataUrlとして、S3保存時は内容のSHA-256をキーにした
`imageKey`として保存されます。複製のたびに写真をブラウザーへ取得して再送信する必要はありません。

## Decision

- `POST /api/gardens/{id}/duplicate`を追加し、フロントは1回だけ呼びます。応答は`GardenSummary`（201）です。
- 所有者は認証済み会員IDで決め、他の会員の庭や存在しない庭は404で何も作りません。
- 1つのMySQLトランザクションで、元の庭の行を`SELECT ... FOR UPDATE`で読み、
  名前・幅・奥行き・`photo_json`（写真・輪郭・四隅・実寸補正・辺の実寸）と全配置を新しいIDで複製します。
  途中で失敗した場合はロールバックされ、複製は残りません。保存（PUT）と同じ行ロックのため、
  保存途中の庭と配置の組み合わせを複製しません。
- 名前は従来どおり「元の名前をUTF-16の54単位で切り詰め＋（複製）」です。サロゲートペアは分割しません。
- 写真は`photo_json`をそのまま複製します。S3保存時は同じ`imageKey`を参照します。
  キーは内容アドレスで、庭を削除しても画像オブジェクトを削除しない既存方針のため、片方の削除で他方の写真は失われません。
- 複製の版番号は新規作成と同じく0です。元の庭の画面キャプチャのサムネイルが現在の版のものなら、
  同じ画像（DBの画像またはS3キー）を版0のサムネイルとして複製します。古い版のキャプチャは複製せず、
  一覧では従来どおり配置図のサムネイルを表示します。
- AI完成イメージの生成履歴は複製しません。従来の複製でも引き継いでおらず、生成時点の庭に対する記録のためです。
  ECで買い物リストへ追加した商品（EC側のデータ）も複製しません。

## Alternatives

- ブラウザーの3回呼び出しを残し、失敗時に作成済みの庭を削除する：削除自体が失敗すると空の複製が残るため採用しません。
- 生成履歴も複製する：大きな画像を含み、複製した別案の生成記録として誤解されるため採用しません。
- S3の写真を新しいキーへコピーする：内容アドレスのため同じキーになり、コピーの意味がありません。

## Consequences

- 複製の通信が失敗した場合、一覧にはエラーと「複製を再試行」を表示し、庭は作られません。
- サーバーの処理は1要求で完了するため、ブラウザーへ写真のdataUrlを往復させません。
- DBスキーマの変更はありません（Alembicマイグレーション不要）。
- 複製名は既存データと画面の表記に合わせて「（複製）」とし、UC-08の記述もこの表記にそろえています。
