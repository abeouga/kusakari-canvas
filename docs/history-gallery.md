# 生成履歴のギャラリーと折りたたみ導線

## Context

キャンバス上に履歴と完成イメージの操作が常時横並びで表示されていた。
履歴一覧は日時・解像度の文字中心で、画像を選ぶまで内容を判別できなかった。

## Decision

- 通常はAI生成ボタン1つだけを表示する。クリックで新規作成／生成履歴の小さなメニューを開く。
  履歴ダイアログを閉じた後、再読み込み後、庭の切り替え後もメニューは閉じた状態にする。
  写真を使わない3D表示では実際の機能に合わせて完成イメージと表記する。
- 履歴はAfterのサムネイルカードをPCで3列、スマートフォンで2列表示する。
  一覧と比較表示を切り替え、戻る操作では選んだカードへキーボードフォーカスを戻す。
  日時だけをカードに表示し、生成方法などは比較画面の閉じた詳細欄に残す。
- 読み取り専用の `GET /api/gardens/{id}/image-history/{historyId}/thumbnail` を追加する。
  既存の庭所有者確認と庭・履歴の対応確認を経てAfterだけを読み、640×400px以内へ縮小する。
  全体の縦横比を保持し、表示もcontainを使う。元PNG・庭スナップショット・DB形式は変更しない。
  一覧メタデータに元画像を埋め込まず、ブラウザーの遅延読み込みを使う。
  クライアントに渡す画像はprivate, no-cacheとし、再取得時にも所有権と存在を確認する。
- 画像を選択したときだけ元画像と撮影情報を取得する。PNG保存は元のバイト列を維持する。
  サムネイルの取得失敗はカード単位で再試行でき、比較や他カードを妨げない。
  履歴削除は確認ダイアログを維持し、失敗時は再試行するまで履歴を残す。

## Alternatives / Consequences

全履歴のフルサイズ画像を詳細APIから先読みする方式は転送・メモリ負荷が大きいため採用しない。
サムネイル列のDB追加も行わず、既存画像から読み取り時に縮小する。
画像のクロップでカードを埋めず、縦長・横長画像には余白が付く。
外側クリック・Escape・Tabによるメニュー閉鎖とフォーカス復帰を扱う。
別変更として反映された撮影補助設定の廃止は保持する。

## Verification

専用MySQL・実API・Chromiumで、初期折りたたみ、5画面幅のメニュー、空の履歴、
縦横比が異なる画像の全四隅、320〜1440pxのギャラリー、比較スライダー、元PNG保存、
一覧・画像・削除の通信障害と再試行、削除確認、22件のページングを検査する。
AI生成は呼び出さず、制御されたPNGを実履歴APIで保存したデータを使用する。
再表示画面・庭JSONをDドライブに保存し、通常DBと専用DBの既存データを比較する。

## 検証結果

専用検証4件が成功。PNGの四隅・縦横比と最大寸法、元画像のバイト一致、必要時だけの詳細取得、
キャンセル付き削除・通信障害からの復旧、22件のページング、写真削除後の履歴閲覧を確認した。
初回の1件は履歴API通信数にCSS読込を誤計上する検査ミスを修正し、全件を再実行して成功した。
通常庭は読み取り専用で1528／390／320px表示を確認し、実際の保存済み3枚を目視した。
起動直後・履歴を閉じた後・再読み込み後は1ボタンに閉じ、開くと履歴が内側に表示される。
既存の履歴テストの導線も更新したが、全E2Eと有料AI生成は実行していない。
証跡は `D:/KusakariVerification/history-gallery-20261019/e2e-final/`。
実利用者の画像を含む画面確認は `private/` に分離し、Gitへ含めない。
lint・対象TypeScript検査・Webビルド・変更したAPIの静的検査も成功した。
ビルドには既存の配信ファイル容量警告が残る。
通常16業務テーブルは検証前後で一致し、専用DBも今回のテスト庭と空カートの除去後に試験前と一致した。
