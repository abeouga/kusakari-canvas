# 写真上の輪郭を固定した辺の実寸編集

## Context

2026-10-21更新。従来は1辺の入力値を倍率として庭全体へ適用していたため、入力していないほかの辺の長さも同じ割合で変わっていた（2026-10-11の方針）。利用者の要求は次のとおり。

- 1辺の長さを変えても、ほかの辺の長さは変わらない。
- 写真上に引いた輪郭の位置・長さ・形・角度は一切変わらない。
- 写真に重ねた輪郭のパースをThree.jsで再現することを最優先とする。
- カメラ情報（撮影端末の画角・姿勢など）は受け取らず、画像だけで実現する。必要以上に複雑な計算を入れない。

## Decision

- `GardenPhoto.edgeLengths` に、輪郭の辺 `boundary[i]→boundary[i+1]` ごとの入力実寸（m）を保存する。未入力の辺は `null`。各辺の表示値は入力値を正本とし、未入力の辺だけ現在の投影から計測した値を表示する。
- 1辺を入力すると、その辺の値だけを更新する。全辺がそろうまではカメラ・寸法・配置物を変更しない。入力済みの辺は常に表示し、未入力の辺数を計測パネルに表示する。
- 全辺がそろった時点、およびその後の各入力で、写真上の輪郭と全辺の実寸からカメラを求め、`calibration.method = 'edges'` として保存する。写真の `boundary` は変更しない。
- カメラは画像中心を主点、正方画素、レンズ歪みなし、水平な地面と仮定する。未知数は縦画角・俯角・傾き・高さの4つ。高さは辺長の比から直接求まるため、反復計算は残り3変数のレーベンバーグ・マーカート法だけで行う（数値微分、3×3の連立方程式）。開始値は現在のカメラとし、収束しない場合だけ画角20〜100度×俯角5〜85度の粗い格子から選び直す。
- 求めたカメラで全辺の3D上の長さが入力値の1%以内に一致しない場合、または縦画角15〜110度・傾き±45度の範囲に解がない場合は適用を拒否し、入力前の庭を維持する。ほかの辺の値を変更して帳尻を合わせることはしない。
- 方位は現在のカメラから引き継ぎ（未校正の写真では奥向き）、輪郭の外接矩形の中心を原点、外接矩形を庭の幅・奥行きとする。配置物は写真上の接地位置を保つよう、新しいカメラで地面座標を求め直す。回転・物体倍率は変更しない。商品の実物サイズを保つため、モデルの見かけの大きさは新しいパースに従う。
- 描画は既存の校正済みカメラと同じ経路（`PerspectiveCamera`、Raycaster、地面投影）を使う。
- 輪郭を描き直した・頂点を動かした場合、辺から求めたカメラは維持し、新しい輪郭の辺長を記録し直す。カメラを求める前の入力値は、辺の数が変わった場合だけ破棄する。基準長方形でカメラを設定し直した場合は入力値を破棄する。
- 空欄、ゼロ、負数、非数値、0.01m未満、100m超、計測不能を拒否する。保存中、カメラ設定中、配置物のドラッグ中、輪郭描画中はUIとstoreの両方で適用を禁止する。

### サーバーでの検証

PUT時、`method = 'edges'` のカメラは、クライアントの行列を信用せず次の条件をすべて満たすことを確認する。反復計算は行わない。

- `edgeLengths` が輪郭と同数で、すべて入力済み（0.01〜100m）。
- 回転行列が正規直交で右手系。縦画角15〜110度。カメラが地面より5cm以上上。
- 全輪郭点が地平線より下にあり、地面上の各辺長が入力値の1%以内。
- 輪郭が庭の幅・奥行きの範囲内（既存の5cmの許容幅）。

基準長方形のカメラ（`method` 省略時）は従来どおり基準点と寸法から再計算する。`edgeLengths` は既存の `photo_json` 列に入るため、DBマイグレーションは不要。旧データは `edgeLengths`・`method` を持たず、従来どおり読み込める。

## Alternatives

- 倍率で庭全体を拡縮する（従来方式）：ほかの辺が変わるため要求に反する。
- 終点を移動して辺を伸縮する：写真上の輪郭を動かすため要求に反する。
- 入力値をラベルとしてだけ保存し、3Dには反映しない：表示と3Dの実寸が一致せず、パースの再現にならない。
- 1辺目の入力時点で、未入力の辺を現在の概算値で固定してカメラを求める：未校正写真の概算値は透視投影として成立しない組合せになることが多く、最初の入力から拒否され続けるため採用しない（模擬写真で確認）。
- EXIFや撮影時の姿勢を使う：カメラ情報を受け取らない要求に反する。

## Consequences・制約

- 1枚の写真と水平な地面の仮定では、未知数が4つのため、四角形は全辺の入力でちょうど解が定まる。五角形以上は条件が未知数より多く、実測値の誤差が1%を超える組合せは拒否される。三角形は解が一つに定まらず、開始値に近い解を採用する。
- レンズ歪み、画像の切り抜きによる主点のずれ、傾斜地には対応しない。真上に近い撮影では画角が不安定になる。
- 輪郭の一致は地面上の対応を示すだけで、植物の高さ方向のパースの正確さを単独で証明するものではない。

## 確認

`npm run test:e2e -- --config playwright.config.ts e2e/photo-scale.spec.ts`。既知のThree.jsカメラ（縦画角50度、位置(5, 8, 13)）で10×8mの長方形を撮った模擬写真を使い、未校正・固定投影・基準長方形校正の3方式で次を確認する。

- 1辺ずつ入力するたびに、入力した辺以外の表示値と写真上の輪郭が変わらない。
- 全辺入力後、カメラ情報を渡さずに縦画角50度・高さ8mを再現し、3D上の辺長が入力値と一致する。配置物の写真上の接地位置が0.1px未満で一致する。
- パース推定後に1辺を11mへ変更しても、ほかの辺の入力値・3D上の長さ・輪郭が変わらない。成立しない組合せは拒否して元の状態を保つ。
- 実API・専用MySQLへの保存と再読み込み後の復元、390px表示。証跡は `artifacts/e2e/photo-scale-*.json` と `.png`。

2026-10-21確認結果：lint、型チェック、Webビルド、API lint・compile成功。上記E2E 3件と関連E2E（polygon-edges 2件、photo-calibration 2件、photo-interaction 5件、garden-dimensions 1件）が通過。隔離E2E設定（`KUSAKARI_AUTH_MODE=demo`、`KUSAKARI_TEST_AUTH=true`）で実行した。

実写真（259×194pxの更地写真、リポジトリ外）でも実UIを操作した。輪郭を4点で描き、写真上の手前・中央・奥に木を置いた状態で、辺を10・12・10・12mの順に入力した。各入力で入力した辺以外の表示値と輪郭が変わらないこと、全辺入力後に縦画角54.9度・カメラ高さ2.14mのパースが求まり、保存されたカメラから求めた3D上の辺長が10.00・12.00・10.00・12.00mになることを確認した。続けて1辺を11mへ変更しても、ほかの辺・輪郭は変わらず、3D上の辺長は11・12・10・12mとなった。成立しない入力（12mの辺を3m）は拒否された。この土地の実測値は未提供のため、10×12mは写真と矛盾しない仮定値であり、実寸の精度を検証したものではない。
