## Context

フェーズ3で生成したAfterはダイアログを閉じると失われました。生成料金を再度支払わずに比較できるよう、生成時のBefore、After、庭データを組として保存します。

## Decision

- MySQLの`garden_image_history`へ庭単位で保存します。Alembic `0003`で追加し、庭削除時は外部キーで履歴も削除します。
- 画像は不透明PNGの元バイト列をLONGBLOBに保存します。撮影時のGardenDocument、参照商品概要、モデル、品質、入力枚数、UTC保存日時も保存します。再保存時の日時は、最初に履歴保存へ成功した日時です。
- 一覧では画像・撮影データを読み込みません。日時とIDのカーソルで新しい順に取得し、詳細を開いた時だけ画像を取得します。
- 全APIは既存のサーバー側所有者判定を使用します。現在の所有者はローカルデモ設定です。
- 生成開始時にUUIDを発行し、生成成功後に自動保存します。同一ID・同一内容の保存は既存結果を返します。内容が異なる場合は409です。
- 保存済み生成IDによる生成要求はOpenAI呼び出し前に409を返します。通信断で生成結果が届かず、保存もされなかった場合の完全な課金重複防止は保証しません。
- 自動保存に失敗しても生成画像を返します。画面は画像を保持し、「履歴へ再保存」で履歴APIだけを呼びます。未保存中は再生成と条件変更を制限し、閉じる・破棄・ページ離脱を確認します。
- Beforeは8MB、合成後Afterは20MB以内です。元写真を含む保存要求は48MB以内、画像の各辺2048px以内・総画素数3,686,400以内を検証します。
- Before／Afterは同じ寸法・座標に重ね、Beforeの表示範囲だけを切り替えます。マウス・タッチ・ネイティブrangeのキーボード操作を使用します。

### API

| 操作 | エンドポイント |
| --- | --- |
| 一覧 | `GET /api/gardens/{gardenId}/image-history?limit=20&cursor=...` |
| 詳細 | `GET /api/gardens/{gardenId}/image-history/{historyId}` |
| 保存・再保存 | `POST /api/gardens/{gardenId}/image-history` |
| 削除 | `DELETE /api/gardens/{gardenId}/image-history/{historyId}` |

保存要求は`id/document/beforeDataUrl/afterDataUrl/model/quality/inputImageCount/referenceSummary`です。詳細は画像と撮影時データを返します。現在の庭の版が変わっても、過去の撮影データを保持します。履歴から現在の庭を上書きする機能はありません。

### 責務

- `history_models.py`：SQLAlchemyテーブル定義。
- `history_schemas.py`：入力・出力DTO。
- `history_service.py`：所有者確認、画像検証、保存・取得・削除、ページ送り。
- `history_routes.py`：HTTP境界。
- `GenerationHistory.jsx`：履歴取得・削除と詳細画面。
- `BeforeAfterComparison.jsx`：画像の重ね合わせと操作。
- `AiImageGeneration.jsx`：生成状態と保存失敗時の復旧。

## Alternatives

- localStorage：端末依存と容量制限があるため採用しません。
- 画像を一覧と一緒に全件取得：通信量とメモリ消費が増えるため採用しません。
- オブジェクトストレージ：本番候補です。ローカルMVPではMySQLトランザクションで画像と撮影データをまとめて保存します。
- 保存失敗時に再生成：課金と結果の変化が生じるため、生成済み画像の再保存を採用します。

## Consequences

画像分だけDBとバックアップの容量が増加します。運用上の保存件数・容量制限は今後の課題です。本番認証とクラウド配置は本フェーズの範囲外です。

## 検証方針

正常系は実FastAPI・MySQL・Chromiumを使います。履歴APIの保存専用データは人工PNGと明記し、AI品質の根拠にはしません。障害系では通信遮断を明示して再取得を確認します。

保存失敗時の復旧は、E2E専用庭だけのINSERTを拒否するMySQLトリガーを一時追加し、実OpenAI生成後にAfterが保持されること、トリガー除去後の履歴再保存だけで復旧することを確認します。正常系APIをモックしません。この確認と正常な自動保存の確認には実生成を各1回使用します。

`ai-image-live.spec.ts`は`KUSAKARI_CANVAS_AI_LIVE=1`と専用APIキーが必要です。障害注入用の`ai-history-recovery-live.spec.ts`は、さらに`KUSAKARI_CANVAS_HISTORY_FAULT_LIVE=1`が必要です。トリガーのために既存DBユーザーへ権限を追加せず、一時MySQLインスタンスで実行します。

旧Flyway/Alembicからの移行、非空PNG履歴を含む再実行、異常スキーマ拒否は一時MySQLインスタンスで確認します。通常のブラウザー操作ではDDL移行前の状態を再現できないため、移行専用検証を使用します。開発用・E2E用DBもバックアップ後に移行し、既存データのハッシュ一致を確認します。

## 検証結果（2026-10-14）

- 履歴API・画面連携は6.1sol / high、比較スライダーは6.1sol / mediumで実装し、Astra / highで設計・実装をレビューしました。
- 履歴のChromium E2E 5件が成功しました。同一IDの並列保存、内容競合409、元PNGバイト一致、撮影時スナップショット保持、カーソル行削除後のページ送り、異なる庭からの取得・削除拒否を確認しました。
- 再読み込み、PC・390px幅、画像位置一致、キーボード・マウス・実タッチ入力、PNGダウンロード、削除の取消・実行、通信遮断後の再取得・再削除、22件の追加読み込み、現在の写真を外した後の履歴比較を確認しました。
- 高エントロピーの不透明Afterは12,627,369bytesで、8MBを超えても保存・取得のバイト列が一致しました。透過PNGと寸法不一致は400で拒否しました。
- Before4件・遮蔽5件・AI事前確認2件・履歴5件の関連16件を実行し、15件が同一実行で成功しました。既存の樹木遮蔽1件はBefore表示待ちで約130秒停止して90秒制限に達しました。時間制限と期待値を変更せず単独再実行し、45.8秒で成功しました。停止原因は未特定です。失敗traceを`artifacts/phase4-regression-timeout/`へ保存し、この実行だけで残った検証庭1件を識別して削除しました。
- 明示した実OpenAI生成は計2回です。正常な自動保存1件、実DB保存失敗からの復旧1件が成功しました。正常保存では生成IDの再送がOpenAI呼び出し前に409となり、画像と庭データが履歴から復元できました。
- 保存失敗時は生成1回のまま、After保持→閉じる確認→再保存の通信断→再保存成功→再読み込み後の比較まで成功しました。履歴再保存は2回で、OpenAI再生成は0回です。
- 障害注入は通常DBのトリガー権限制限で生成前に停止したため、一時MySQLで検証しました。既存DBの権限・サーバー設定は変更していません。一時インスタンスは停止・削除済みです。
- 開発用・E2E用を0002から0003へ更新し、既存の庭・写真・配置のハッシュが更新前と一致しました。一時MySQLで新規作成、Flyway v1/v2、Alembic v1/v2、非空履歴の再実行保持、不正スキーマ、不正移行履歴の8条件を確認しました。
- 検証終了後も開発用・E2E用の既存データのハッシュが開始前と一致し、残った検証履歴・障害注入トリガーは0件でした。今回起動したEC検証サーバーも停止しました。
- JS/Python lint、E2E型チェック、Python compile、Web本番ビルドが成功しました。従来の500kB超チャンク警告は残ります。秘密キーの値は表示せず、`.env`のGit除外とGit対象候補ファイルへの混入がないことを確認しました。

主な証拠は`artifacts/e2e/history-*`、`ai-live-*`、`phase4-db-before.json`、`phase4-db-after.json`、`artifacts/fastapi/phase4-isolated-migrations.json`、`phase4-isolated-live-recovery.json`です。人工写真と検証用GLB・参考画像を使用しています。実庭・実商品の写真による生成品質の評価はフェーズ5です。
