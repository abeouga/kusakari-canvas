## Context：問題と根拠

前回は同じ入力でmedium/highを各1回生成し、植物の幅が約1.44倍／約1.41倍になりました。実送信画像・指示・マスクの一致とAfterの全画像採用は確認済みです。品質設定だけでは、この入力の寸法保持条件を満たせませんでした。[前回の評価](ai-quality-medium-high-evaluation.md)

現行`ai_prompt.py`には主画像の優先、寸法保持、参考写真を外観だけに使う指定がすでにあります。「指定し忘れているから拡大した」とは言えません。主画像優先の繰り返し、家具・遮蔽の長い説明、複数箇所の禁止表現を整理する余地はありますが、それが失敗原因であるという証拠はありません。

公式ガイドは、変更箇所と保持条件を明確にし、複数の参考画像へ役割を割り当て、一度に変える条件を限定する方針を示しています。短文が常に優れるという保証はありません。今回の候補はこの整理方針に沿う独自の指示です。[OpenAI公式画像プロンプトガイド](https://developers.openai.com/api/docs/guides/image-prompting)

## Decision：候補指示

候補は[テンプレート](prompts/scene-layout-v2-template.txt)です。冒頭で「画像1の庭全体にある植物だけを実写化する」と指定し、続けて次の4項目を各1か所にまとめます。

1. GEOMETRY：画角、位置、幅・高さ、輪郭、幹、接地を維持して葉・樹皮の外観を付ける。
2. IMAGE ROLES：主画像が構図と可視状態の基準。補助は同じ庭・画角で隠れた植物を識別するための画像。参考写真は葉・樹皮の見た目だけを提供する。
3. PRESERVATION：庭背景・家具・遮蔽を維持する。家具の形状・部品・素材、完全遮蔽と部分遮蔽の扱いを残す。
4. COORDINATES AND OUTPUT：座標・bounds・visibleBounds・anchorの意味、マスクの余裕、白い余白、全画像出力を指定する。

既存の`IMAGE ROLES`と`IMAGE 1 PLACEMENTS`のJSONは同じ順序・値・文字列のまま末尾に付けます。商品名やplacement IDも省略しません。本文の章名IMAGE ROLESと、末尾の`IMAGE ROLES:`データ見出しは区別します。画像枚数を条件分岐して文章を省くことも、今回は行いません。

| ケース | 現行の全文文字数 | 候補の全文文字数 | 変更対象 |
| --- | ---: | ---: | --- |
| 単体 | 3,775 | 2,905 | 自然言語の指示本文 |
| 重なり | 5,915 | 5,045 | 同じ指示本文 |

文字数はUTF-8で読み取った文字列の長さで、トークン数ではありません。候補は約870文字短くなっています。長さだけでなく言い回し・順序・visibleBoundsの説明も変わるため、検証できるのは「候補本文全体」の効果です。「短縮そのものの効果」とは呼びません。

完全な比較用テキストは`artifacts/e2e/ai-quality/prompt-revision-design-01/`の`single-control.txt`、`single-candidate.txt`、`overlap-control.txt`、`overlap-candidate.txt`です。`design-manifest.json`に各ハッシュ、固定入力、文字数を記録しました。末尾データの完全一致をオフラインで確認済みです。保存時はUTF-8、BOMなし、LF、末尾改行なしで全文をハッシュ化します。旧証拠のCRLFは読み込み時にLFへ正規化して比較します。

## 固定する条件

| 項目 | 固定値・規則 |
| --- | --- |
| APIモデル | `gpt-image-2.5-sunburst`。同名モデルの提供側更新までは固定できないため日時を保存 |
| 品質 | 両群ともmedium。通常設定と同じにし、前回のmediumを補足資料として残す |
| 画像と配置 | `layout-revision-03`のBefore・coverage・補助・参考写真・順序・layoutをそのまま使用 |
| 単体の画像数 | 主画像1＋植物参考1＝2枚。3D単体の切り抜きは使用しない |
| 重なり | 固定基線の補助4枚と参考写真・配置を維持。最初の生成対象には含めない |
| サイズ | 元1280×853、API1280×1024。右・下だけ余白追加、出力はその余白だけを除去 |
| マスク | 同じ画素とハッシュ。8pxの余裕、家具境界の扱いを変えない |
| リクエスト | images.edit、n=1、PNG、不透明、既存timeout=180・retry=0。その他のパラメータを追加しない |
| 出力 | API出力全体をAfterとして保存。位置合わせ・拡縮・貼り戻しを加えない |
| 実行環境 | 同一の保存ビルド、同一コード、同じ商品参考情報。両群を同じ評価時期に順次実行 |

今回の差分は指示本文だけです。前回のhigh出力と今回のmedium候補を直接比べて指示の効果とは判定しません。前回出力を加工して次の入力に使うこともありません。

## 生成前に必要な測定条件

許容値は旧評価計画から変えません。植物の位置8.53px、幅・高さ±10%、指定背景点4.265pxです。必須条件が判定不能なら合格にはできません。

前回の測定誤差には、合格を確定できない問題があります。元の幅99px、元の端点誤差±2px、今回の端点誤差±5pxとすると、測定幅をwとして比率区間は`[(w-10)/103, (w+10)/95]`です。この区間全体を0.90〜1.10に収めるには、wが102.7以上かつ94.5以下である必要があり、両立しません。前回の幅の不合格は下限でも1.10を超えるため有効ですが、この精度では合格を確定できません。

次の実装・無課金確認では、保存済みBefore/Afterを使って測定手順を確定します。

- 原寸画素座標を読める表示で、外形と葉の境界、可視接地点、樹冠中心の定義を記録する。表示上の拡大は可能ですが元画素の補間結果を測定対象にしません。
- 端点の読み取り誤差は±1pxを目標にします。実際に境界をその精度で特定できた場合だけ使用し、先に±1pxと決めつけません。曖昧な影を植物の外形へ含めません。
- 同じ画像の繰り返し読み取りと、保存された画素範囲との照合を記録します。一致だけで真の誤差が証明されたとは扱わず、判別できる境界があることも確認します。
- 元の誤差±2px、出力±1pxなら幅比の区間は`[(w-2)/103, (w+2)/95]`となり、w=99pxの例は約0.942〜1.063です。合格を判定できる精度になります。高さ・位置も各点の誤差を含めます。
- 左の枝の分岐`[139,274]`と奥の白い柵の端`[1023,550]`は、従来と同じ対応点を手動で特定する。自動追跡の相関0.8未満を成功へ丸めず、別の点に差し替えません。
- 測定手順と担当の読み取り記録を生成前に保存します。既存画像で必要な精度・対応点を確立できなければ、新たな課金比較を開始せず、測定上の限界を報告します。新しい出力で判別不能になった場合も合格扱いにしません。

この手順は測定の改善です。許容値の緩和、前回の不合格取り消し、背景の完全画素一致を新たに要求する変更ではありません。

## 実験の順序と停止条件

| 段階 | 順序 | 生成上限 | 次へ進む条件 |
| --- | --- | ---: | --- |
| 今回 | 指示と計画の固定 | 0 | 完了 |
| 次の実装 | 指示選択・証拠記録・測定手順の無課金確認 | 0 | 固定条件照合と測定準備を満たす |
| 単体探索 | 現行A → 候補B、各1回、両方medium | 2 | Bの全必須条件が合格 |
| 単体再確認 | 候補B → 現行A、各1回、両方medium | 累計4 | Bの2枚がともに全必須条件合格 |

候補の不合格または判定不能で停止します。対照Aが品質不合格でも、候補Bの比較は実行できます。通信失敗、送信済みか不明、証拠欠落、固定入力不一致ではその場で停止し、自動再試行しません。保存だけ失敗した場合は取得済み画像の再保存を使います。

背景・自然さ・旧3Dの残り・サイズ・位置・余白除去後の一致・履歴再表示を別項目に記録します。葉が自然なだけでは採用できません。AもBも合格した場合は改善効果が未確定、Bだけ合格した場合も少数例での採用候補にとどめ、統計的優位性とは呼びません。

重なり用テキストはデータの保持を確認するために今回固定しました。単体が合格した後に、ベンチの背・座面・脚の同一特徴点と植物の可視断片を事前注記して別段階を準備します。今回の計画は重なり・複数配置の自動連続実行を含みません。

## 次の実装範囲：可読性と責務

通常利用の指示は`scene_layout_v1`を維持します。候補を評価専用設定から選べるようにします。クラス階層や汎用テンプレートエンジンは追加せず、既存の設定クラスと名前付き関数を使います。

| ファイル | 必要な変更 |
| --- | --- |
| `ai_config.py` | `AiSettings`末尾へ`prompt_version`を追加。評価時だけ`KUSAKARI_CANVAS_AI_EVAL_PROMPT_VERSION`でv1/v2を許可。e2e、二重実生成フラグ、証拠保存先、明示quality、計画ファイルを必須にする |
| `ai_prompt.py` | `generation_prompt`で明示的なifにより本文を選択。本文生成と既存の画像役割・配置JSON生成を小さな関数に分ける。v1全文のハッシュを維持。v2はこの候補全文と一致させる |
| `ai_service.py` | 設定の指示版を生成関数へ渡す。画像準備・余白除去・保存順序は維持 |
| `ai_evidence.py` | 現状の固定`PROMPT_VERSION`記録を実際の設定値へ変更。本文の実ハッシュと一致確認 |
| `ai_evaluation.py` | 新計画で指示版と全文ハッシュを照合。版がない旧計画はv1に限り既存ハッシュ検証を継続。v2の版なし計画は拒否 |
| `verification/run_ai_quality.py` | 版を明示する引数を追加。まず旧v1基線の一致を検証し、その後選択版を今回固定した候補ハッシュと照合する。既存の「旧指示と一致」の判定を削除して通す方法は採用しない |
| `e2e/ai-quality-evidence.ts` | 実際の指示版と計画ハッシュの一致を検証。既存の固定入力・履歴・PNGの検証を残す |

候補の期待ハッシュは、実装時にその場で生成した本文から作って自己一致させるのではなく、今回固定した`design-manifest.json`を根拠にします。マニフェスト全体は実行用計画ではありません。`executionReady=false`であり、測定条件を満たした後に、選択したケース・版・品質・一意なrun名から1回分の実行計画を作ります。

HTTP要求・画面に指示の選択を追加しません。DBの履歴形式・スキーマも変更不要です。通常v1の生成で指示全文が変わらないこと、不正版・devでの上書き・v2と旧計画の不一致を無課金で確認します。キーを空にした画面テストは送信前段の一部しか通らないため、指示組み立て・設定検証・計画拒否はオフライン検証を併用します。成功APIをモックしません。

## Alternatives / Consequences

候補は可読性と条件の整理を目的にした仮説であり、成功を保証しません。候補も不合格なら、禁止文の追加を繰り返さず原因を再評価します。参考写真の影響やマスクの余裕を変える案は別実験です。今回には混ぜません。全画像採用・庭の画角固定という方針は継続します。

今回の成果物は候補本文、完全な対照テキスト、ハッシュ、比較手順、測定上の事前条件、実装範囲です。製品コードの修正や追加生成は0件です。次は6.1sol / highを担当設定とする実装・無課金確認、その後の実画像評価はAstra / highです。これは役割の割り当てであり、このチャットの実行モデルの切り替えを証明するものではありません。
