# 写真と多角形地面、写真上への配置物の表示

校正済み写真の撮影カメラは[写真のカメラ校正](photo-camera-calibration.md)、辺の実寸入力は[写真上の辺の計測](polygon-edge-editing.md)を参照。この文書は、写真・輪郭の保存形式と、写真上に3Dモデルを重ねる方法を扱う。

## Context

庭は幅・奥行き、配置物、revisionを持つ`GardenDocument`で、3D表示とMySQL保存が動作する。写真の上で「1→2→3→4→5…→1」の一連のクリックで任意の輪郭を閉じ、3D庭で置いた木を写真上にも実際の3D形状で表示し、写真上でも配置できる必要がある。

## Decision

### 写真と輪郭の保存

- 写真の元データはJPEG/PNGのdata URLとして`GardenDocument.photo`に入れ、revision付きPUTで保存する。最大5MB、各辺6000px、総画素数2500万、輪郭64点まで。写真のない庭の`photo`は`null`。保存形式は後方互換の`schemaVersion=1`の任意項目として扱う。画像の保存先は既定でMySQL（`KUSAKARI_CANVAS_MEDIA_STORAGE=database`）で、`s3`を指定した環境では非公開のオブジェクトストレージに置く。API DTOの形は変わらない。
- 写真読み込み直後から3〜64点の単純多角形を描く。最初のクリックが庭の頂点1であり、4点目でも描画状態・点列を維持する。最後の頂点からポインターへの仮線を表示し、3点以上で始点1をクリックした時だけ検証済みの輪郭をGardenDocumentへ反映する。描画途中に閉じた面やグリッドは表示しない。
- `boundary`は元画像に対する0〜1の輪郭点列とする。交差、面積不足、画像外、重複や近すぎる点を拒否する。最後に始点を重複追加しない。
- `corners`はユーザー入力ではなく、輪郭の外接矩形から「下左→下右→上右→上左」の順で自動生成する内部の変換基準である。外接矩形を庭の幅・奥行きへ対応させ、3×3変換とR3F地面メッシュ生成へ渡す。描画した多角形を四角形に置き換えない。
- 描画途中の頂点はZustandの一時状態として保持し、API DTOへ含めない。描画中は保存と3D切替を止め、取消時は以前の確定済み輪郭・変換を保持する。輪郭を確定し直す、または確定済み頂点をドラッグした時に外接矩形から変換基準を更新する。
- 頂点番号は描画中だけ表示する。確定後は番号のない頂点ハンドルのドラッグと「庭の領域を書き直す」で修正できる。取消では以前の輪郭を保持し、配置物を自動削除しない。

### 写真上への配置物の表示

- 写真の上に透明なR3Fキャンバスを重ねる。GardenDocument.objectsを3D庭と共有し、GardenModelで同じGLB、回転、倍率、位置を描く。写真と3D庭は同じ配置データ・モデル読み込み・失敗表示・地面への配置処理（GardenGround）を使う。OrbitControlsは3D庭だけで使う。
- カメラは保存済みの地面変換と庭寸法から再生成する表示状態であり、GardenDocumentやDBへThree.jsオブジェクトを保存しない。校正済み写真は撮影カメラを再現した`PerspectiveCamera`を使う（[写真のカメラ校正](photo-camera-calibration.md)）。
- 校正データのない写真は、`OrthographicCamera`を土台に投影行列を固定する近似を使う。地面Y=0の根元位置は写真座標に一致させ、高さYは画像の縦座標だけに加える。画面の左右でも幹と選択枠の縦辺が垂直になる。高さの表示倍率は庭中心の幅方向の1mに対応する画素数から求める。projectionMatrixInverseも更新し、Raycasterは同じ逆行列で深度中央付近の2点を逆投影して生成する。
- 写真の表示サイズに合わせて、実際のキャンバス矩形からポインターを正規化し、同じ地面メッシュにレイを当てる。輪郭外、視点を動かすためのドラッグ、保存中のクリックでは配置しない。
- 写真の「地面」「グリッド」「配置物」の表示を個別に切り替えられる。

## Alternatives

- 画像をブラウザーの一時URLやlocalStorageに置く方法は、再読み込み後・別端末での復元に適さない。
- 四隅の手動指定を必須の前段に残す方法は、一連の頂点クリックで輪郭を描く操作要件を満たさない。任意多角形の頂点だけでは各頂点の実測3D座標が不明なため、正確な遠近補正の対応点として扱わない。
- 丸いマーカーや木のアイコンだけでは、Three.jsモデルの重ね表示にならない。写真用に別のモデルや別の配置リストを持つと、両画面の位置・回転・倍率と保存状態が食い違う。
- 未校正写真で有限距離のカメラ中心を仮定する方法は、高さによって横位置も変化し、画面端の木が斜めに見えた。地面の対応だけでは垂直方向の消失点に根拠がないため、垂直方向を平行にする。

## Consequences

庭のJSON応答とPUTは画像分だけ大きくなる。写真の変更は庭の自動保存で確定し、競合時は既存のrevision検査を適用する。輪郭の変更後に既存配置物が地面外となっても、配置物の自動削除や位置補正は行わない（範囲外の配置がある間は保存しない。[配置範囲](placement-bounds.md)）。3Dグリッドは0.125m刻みで表示区間を近似して切り取る。

外接矩形による対応は写真の奥行き歪みを推定・補正しない。写真上の輪郭の形状を3D平面へ写す機能であり、地面の実測形状を写真だけから復元したとは主張しない。頂点や輪郭を変更すると、既存オブジェクトの3D座標を保ったまま写真上の根元位置が変わる場合がある。写真内の既存物による遮蔽、現実の照明・影の再現は行わない。写真画面でもWebGLとGLB読み込みが必要になる。

Three.jsのカメラ行列とレイ生成の契約は[Camera](https://threejs.org/docs/pages/Camera.html)と[Raycaster](https://threejs.org/docs/pages/Raycaster.html)を参照した。
