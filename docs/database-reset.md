# Canvas の DB を初期化して作り直す（issue #63）

## Context

EC の店舗側アカウントの作り直し（abeouga/kusakari-ec#103）では、EC の DB を初期化して会員を作り直す（abeouga/kusakari-ec#106）。会員を作り直すと会員 ID が変わるので、Canvas の庭は誰のものでもなくなる。EC の買い物リストが持つ庭 ID も、Canvas の庭と食い違う。そこで、Canvas の DB も初期化して作り直す。

他の PC は `setup.bat` で環境を作っていて、PC によって MySQL の場所が違う。

- すでに MySQL が入っている PC（existing）：多くは 3306 番ポート。EC やほかのプロジェクトの DB と同じ MySQL を使っていることがある
- セットアップが専用の MySQL を作った PC（managed）：Canvas のデータフォルダー（既定はユーザーのローカルデータフォルダーの `KusakariCanvas`）の `mysql\instance.json` に記録されたポートを使う

`setup.bat` は既存のデータを消さない方針で、DB を作り直す手段がなかった。対象を取り違えると、別のプロジェクトや開発者の庭を消してしまう。

## Decision

`DB-reset.bat`（`scripts/reset-database.ps1` から `python -m kusakari_canvas_api.reset_database` を呼ぶ）を追加する。その PC で Canvas が使っている MySQL を特定し、Canvas の DB だけを消して、その時点のマイグレーションで作り直す。起動時には何も消さない。Windows の管理者として実行する。

### 実行のしかた

1. Kusakari Canvas（`start.bat`）を終了する
2. `DB-reset.bat -DryRun` を実行する。Windows の確認（ユーザー アカウント制御）が出るので「はい」を選ぶ。別のウィンドウが開き、対象が表示される。この時点では何も変更しない
3. `DB-reset.bat` を実行する。同じように Windows の確認の後、別のウィンドウに対象が表示されるので、合っていれば `RESET kusakari_canvas` と入力する
4. 「Canvas の DB の初期化が完了しました」と表示されたら、`start.bat` で起動する
5. EC の DB をまだ初期化していないときは、EC 側の `DB-reset.bat` も続けて実行する（abeouga/kusakari-ec#106）

| 引数 | 動き |
| --- | --- |
| なし | 対象を表示し、確認の文字の入力を求める |
| `-DryRun` | 対象を表示するだけで終了する。何も変更しない |
| `-NoBackup` | 消す前のバックアップを取らない |
| `-ConfirmText "RESET kusakari_canvas"` | 確認の文字を引数で渡す。動作の確認用で、ふだんは使わない |

終了コードは、成功が 0、エラーが 1、確認の文字が違って中止したときが 2。Windows の確認で「いいえ」を選んだときは、何も変更せずに終了コード 1 で終わる。

管理者として起動し直したウィンドウは、結果を読めるように、最後に Enter キーの入力を待つ。すでに管理者として開いた PowerShell から実行したときは、そのまま同じ画面で進む。

### 対象の決め方

消す DB は、開発用の `kusakari_canvas` と、E2E 用の `kusakari_canvas_e2e`（この名前で始まる DB）の2つ。接続先と DB 名は、セットアップと同じ規則（`setup_database.profile_config`）で `.env` と `.env.e2e` から読む。この規則は、ほかの名前の DB を受け付けない。

次のすべてを確かめる。1つでも確かめられなければ、何も変更せずに止まる。

- 開発用と E2E 用が、同じ MySQL の別の DB を指している
- 設定のポートで MySQL が応答している。専用の MySQL が停止しているときは、起動時と同じ処理で起動する
- そのポートを待ち受けているプロセスが1つだけで、`mysqld.exe` である
- 接続した MySQL 自身が答えるポートが、設定のポートと同じである。開発用と E2E 用の接続先が、同じサーバーである
- 専用の MySQL（managed）のときは、記録（`instance.json`）のデータの場所が、接続先と一致する
- 既存の MySQL（existing）のときは、接続先が専用の MySQL のデータの場所ではない。設定が、専用の MySQL の古いポートを指していない
- 対象の DB にテーブルがあるときは、Canvas のマイグレーション履歴（`alembic_version`）がある。なければ、別の用途の DB の可能性があるので止まる
- それぞれの DB のユーザーに、DB を作り直す権限（`CREATE` と `DROP`）がある
- 対象の DB に、ほかのプロセスが接続していない（Canvas や E2E が動いていない）
- 画像を DB に保存する設定である（画像を S3 に保存する設定の環境は対象外）

### 消す前に表示するもの

MySQL の方式、ポート、プロセス ID、実行ファイル、データの場所、バージョン、消す DB ごとのユーザー・テーブル数・マイグレーションの版・主なテーブル（庭、配置、サムネイル、画像生成の履歴）の行数。

### 実行すること

1. テーブルのある DB を、セットアップと同じバックアップの処理（`mysqldump`）で保存する。保存先は `KUSAKARI_CANVAS_BACKUP_DIR`、指定がなければ Canvas のデータフォルダーの `backups`
2. 2つの DB を削除して、空の DB を作る（照合順序はセットアップと同じ `utf8mb4_0900_ai_ci`）
3. セットアップと同じ確認を行う。DB ごとに Alembic を最新まで適用し、テーブルの構成と初期アセットを確かめる

3 の処理は `setup_database.migrate_and_verify` に移し、`setup.bat` と同じものを使う。

### 決めたこと（#63 の「決めること」）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| E2E 用の DB も一緒に初期化するか | する。開発用と E2E 用を必ず一緒に作り直す | 2つの DB は同じマイグレーションで作るもので、片方だけ古い構成が残ると E2E が失敗する |
| 確認の方法 | 対象を表示した後に、決まった文字（`RESET kusakari_canvas`）の入力を求める。表示だけを行う `-DryRun` も用意する | 「はい／いいえ」より、押し間違いで消すことが起きにくい。EC のスクリプトと文字を変えて、取り違えにくくする |
| EC の初期化と一度に実行できるようにするか | しない。EC と Canvas のスクリプトを続けて実行する | EC は別のリポジトリで、置き場所が PC によって違う。まとめて実行する手順は abeouga/kusakari-ec#113 で扱う |
| existing の MySQL で、DB を作り直す権限をどう得るか | Windows の管理者として実行する。起動したときに、Windows の確認（ユーザー アカウント制御）を求める。DB の操作は Canvas 用のユーザーで行い、MySQL の管理者（root）のアカウントは聞かない | ユーザー判断（2026-11-12）。abeouga/kusakari-ec#102 決定事項2 の「管理者権限で実行するスクリプト」に合わせる。DB の操作そのものは、セットアップが Canvas 用のユーザーに付けている権限（自分の DB へのすべての権限）で足りる。権限が自分の DB に限られているので、ほかの DB を消すことができない |

## Alternatives

- EC だけを初期化して、Canvas は残す：庭の持ち主と、EC の買い物リストが持つ庭 ID が、作り直した EC と食い違う
- MySQL のデータフォルダーごと初期化する：同じ MySQL に EC やほかのプロジェクトの DB があると巻き込む
- MySQL の管理者（root）で接続して作り直す：root のパスワードを聞く必要があり、root はどの DB でも消せるので、対象を取り違えたときの被害が大きい
- Windows の管理者権限を求めない：DB の削除と作成そのものには要らないが、ユーザー判断で、管理者として実行する形にした（最初の実装は管理者権限を求めない形で、2026-11-12 に変更した）
- テーブルだけを削除して DB は残す：テーブルの一覧を取り違える余地がある。DB ごと作り直す方が、残るものがない
- バックアップを取らない：移行しないと決まっているが、消した後で必要になったときに戻す手段がなくなる。`-NoBackup` で省ける
- 起動時に、DB が古ければ自動で作り直す：「起動時に既存データを消さない」規約に反する

## Consequences

- Windows の管理者権限を持たないユーザーは、このスクリプトを実行できない。表示だけの `-DryRun` も、管理者として実行する
- 起動した人と違うユーザーの管理者権限で実行すると、設定や専用の MySQL の記録の場所が変わり、対象を取り違えるおそれがある。この場合は何も変更せずに止まる
- 消した DB のデータ（庭・配置・写真・サムネイル・画像生成の履歴）は、すべて失われる。写真と生成した画像は DB の中に保存されているので、一緒に消える
- バックアップは Canvas のデータフォルダーに残り、Git には入らない。庭の写真を含むので、共有しない
- Canvas だけを初期化すると、EC の買い物リストが持つ庭 ID が、存在しない庭を指す。EC 側も続けて初期化する
- DB を作り直した後でマイグレーションに失敗すると、DB は空か、途中まで作られた状態で残る。原因を直してから `setup.bat` を実行すると、テーブルが作られる
- `setup_database.py` は、マイグレーションと初期アセットの確認を `migrate_and_verify` という関数に移した。処理の中身は変えていない
- 庭の持ち主の列を EC の会員 ID に合わせる変更と、マイグレーションのまとめ直しは、この変更に含めていない（#64）

## Verification scope

開発者がふだん使っている MySQL（3306）では試していない。使い捨ての MySQL 8.0.46 を別のポート（33999）に一時的なデータフォルダーで立て、セットアップと同じ権限の開発用・E2E 用のユーザーを作って確かめた。同じ MySQL に、EC の DB（`kusakari`、`kusakari_e2e`。それぞれ21テーブル）と、別のプロジェクトに見立てた DB を置いた。Canvas のデータフォルダーは一時的なフォルダーに向けた。18の場面は、初期化の処理（`python -m kusakari_canvas_api.reset_database`）を直接実行して確かめた。この処理は、管理者権限のない状態でも DB の削除と作成ができた。

### 検証結果（2026-11-12）

18の場面がすべて期待どおりだった。

| 場面 | 結果 |
| --- | --- |
| `-DryRun`（空の DB、データのある DB） | 対象とテーブル数・マイグレーションの版・行数を表示し、データは変わらなかった |
| 初期化（空の DB） | 2つの DB が最新のマイグレーション（`0008`）まで作られ、初期アセットがあった |
| 初期化（データのある DB） | 目印を付けたデータが消え、作り直された。消す前のバックアップが2つの DB 分でき、目印のデータを含んでいた |
| `-NoBackup` | バックアップを作らずに初期化できた |
| 同じ MySQL のほかの DB | 初期化の後も、EC の DB（21テーブルずつ）と別のプロジェクトに見立てた DB のデータが残っていた |
| 確認の文字が違う（小文字で入力） | 終了コード2で中止し、データが残った |
| 設定のポートで何も応答しない | 何も消さずに止まった |
| 設定のポートを MySQL 以外のプロセスが使っている | 何も消さずに止まった |
| 対象の DB にマイグレーション履歴がない | 何も消さずに止まった。もう片方の DB も消えなかった |
| ほかのプロセスが対象の DB に接続している | 何も消さずに止まった |
| 片方の DB を作り直す権限がない | どちらの DB も消さずに止まった |
| 専用の MySQL（managed）で、記録と接続先が一致する | 初期化できた |
| 専用の MySQL の記録と、データの場所が違う | 何も消さずに止まった |
| 設定が、専用の MySQL の古いポートを指している | 何も消さずに止まった |
| 設定は既存の MySQL なのに、接続先が専用の MySQL のデータ | 何も消さずに止まった |

あわせて、次を確かめた。

- 初期化した E2E 用の DB に対して実 API を起動し、庭を作る → 読み直す → 保存する → 読み直す、が通った。読み直した庭の名前・幅・版が、保存した内容と一致した。認証は、明示した隔離テスト用の設定（E2E のプロファイルと、テスト用の認証）を使った
- 管理者でないときに、管理者として起動し直す処理：起動の部分を置き換えて（Windows の確認を出さずに）、渡す引数（表示だけ・バックアップなし・確認の文字・起動した人のユーザー名）が正しく組み立てられること、起動が取り消されたときに「DB は変更していません」と表示して終了コード1になること、引用符を含む確認の文字を受け付けないことを確かめた
- 管理者権限を求める形に変える前に、`DB-reset.bat` から起動して、`-DryRun` が終了コード0、確認の文字が違うと終了コード2、Python の実行環境がないと終了コード1になることを確かめた

### 確かめていないこと

- Windows の確認（ユーザー アカウント制御）を実際に通して、管理者として起動し直した後の動き。確認の画面を操作できない環境で検証したため。管理者として起動した後に行う処理（起動した人との照合、Python の実行環境の確認、初期化の処理の呼び出し、最後の Enter 待ち）は、まだ実際には動かしていない
- Chromium の E2E（画面から庭を作って保存・再読み込みする操作と、スクリーンショットの保存）。確かめたのは、実 API と MySQL まで
- 3306 の既存の MySQL と、セットアップが作った専用の MySQL そのもの。専用の MySQL は、記録の場所を一時的なフォルダーに向けて、同じ判定を通ることだけを確かめた
- 画面で確認の文字を入力する操作（確認の文字は引数で渡した）
- 専用の MySQL が停止しているときに、スクリプトが起動する動き（試験では起動した状態で実行した）
- 1つのポートを複数のプロセスが待ち受けている場合
- `setup.bat` の全体。変えたのはマイグレーションと確認の処理の呼び出し方だけで、同じ処理が初期化スクリプトから通ることを確かめた
- MySQL 8.4 のサーバー（使い捨ての MySQL は 8.0.46）
- 他の PC での実行
