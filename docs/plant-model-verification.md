# 植物の商品連携の検証結果

確認日：2026-10-16

## ゴール

出品者が入力した植物の特徴から、事前制作した共通GLBパーツの組み合わせが決まり、その商品をCanvasへドラッグすると、対応する植物を配置・保存・復元できること。

## 確認結果

- 実EC画面で樹木・低木・草花を各2パターン登録し、プレビューと保存された構成が一致した。
- 商品一覧から6個、カートから1個、クリック操作から1個を配置できた。
- 回転・拡縮を含む8個の配置を保存し、再読み込み後の実API JSONが完全一致した。
- 商品の特徴変更後も、保存済みの庭は以前の構成を保持した。
- 写真上で旧ベンチと植物を混在させ、追加ドラッグ後の10個の配置を保存・復元できた。
- 未設定商品の配置不可、構成改ざんの拒否、高さ不整合の拒否、旧クライアントの在庫更新時の構成保持を確認した。
- 配置数量からの商品候補照合は、対応する商品だけを返した。CanvasとECは同じカートを表示した。
- 右サイドバーの幅変更と再読み込み後の幅保持、下部カテゴリナビゲーションの撤去を確認した。

Canvas APIのCRUD、写真、検証、同時更新、ロールバック、所有者分離の検証は通過した。最初の `npm run verify:api` は移行検証用DBを作成する権限不足で終了したため、コマンド全体の成功とは扱わない。移行検証は別の隔離した実MySQL 8.0.46で全10ケースを実行し、成功・期待した不正スキーマの拒否・再起動時のデータ保持を確認した。この一時MySQLは停止済み。

両フロントの静的確認・ビルド、Pythonの静的確認・コンパイル、Javaビルドは通過した。通常のEC（5186 / 8086）とCanvas（5173 / 8080）は起動中。通常DBの既存業務データは、起動前後の行数とハッシュで保持を確認した。

## 検証環境の補足

Windowsのheadless-shellはSwiftShaderによるCPU描画だった。多数の植物を配置する操作で時間超過したため、実GPU（AMD / Direct3D11）を使用できる通常のChromiumへ切り替えた。同じ配置・保存・復元の判定条件でE2Eを通過した。テスト設定はこのブラウザを指定し、失敗時のtraceと明示的な成果物の画面保存を維持する。

初期GLBは汎用の6パーツ。個別植物の写真どおりの形状再現は、この検証の完了条件に含めていない。
