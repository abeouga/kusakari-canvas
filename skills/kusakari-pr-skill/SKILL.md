# PR・Issueの本文を、テンプレートを守りつつ「要約」と「原文」で書く

## このスキルが解決する問題

PRやIssueの**構造はテンプレートで決まっている**。問題は**各見出しの中身**で、
AIに書かせると次のようなことが起きる。

- 「概要」に関数名やファイルパスが並び、何が変わったのか読み取れない
- 「なぜ」が書かれず、「何をしたか」の作業ログになっている
- レビュアーに必要な情報と、次の作業者（AI）向けのメモが同じ段落に混ざっている
- 確認していないことが、確認済みのように書かれている

このスキルでは、テンプレートの見出しは一切変えず、本文を**「要約」と「原文」の2層**にする。

- **各見出しの下（要約）**：その見出しの原文を要約したもの。人間が読んで理解し、判断できる文章
- **本文の一番下の `<details>`（原文）**：全セクションについて、書くべきことを省略せずにすべて書いた全文。ファイルパス・関数名・コマンド・却下した案・次の作業者への指示まで含む。**どのセクションの原文かを必ず明記する**

要約は原文から作る。**原文にないことを要約に書かない。** 原文だけを読んでも全セクションの内容がすべて分かり、要約だけを読んでも判断できる状態にする。

## 手順

1. **テンプレートを特定する**
   - PR：`.github/pull_request_template.md`、`.github/PULL_REQUEST_TEMPLATE/` 配下、ルートや `docs/` 配下の同名ファイル
   - Issue：`.github/ISSUE_TEMPLATE/` 配下。`.md` なら見出しをそのまま使う。`.yml`（Issueフォーム）なら各フィールドの `label` が見出しになる
   - テンプレートが複数あれば、内容に合うものを選ぶ。迷ったらユーザーに聞く
   - テンプレートが見つからない場合だけ、末尾の「テンプレートがない場合」を使う

2. **材料を集める**
   - PR：`git log <base>..HEAD` と `git diff <base>...HEAD --stat`、必要なら差分本体。最新コミットだけでなくブランチ全体を対象にする
   - Issue：ユーザーの説明、エラーログ、再現手順、関連コード
   - このセッションでの会話（なぜその実装にしたか、却下した案など）も材料にする

3. **先に全セクションの原文を書き、次にセクションごとに要約する**（下の「書き方」）

4. **ユーザーに本文を見せて確認を取る**
   - 承認されたら `gh pr create --body-file <file>`、`gh pr edit --body-file <file>`、`gh issue create --body-file <file>` などで反映する
   - 本文はファイル経由で渡す。`--body "..."` は改行や記号が崩れやすい

## テンプレートの扱い

- 見出しの文言・順序・階層を変えない。見出しを追加・削除しない（一番下の原文の `<details>` は見出しではないので追加してよい）
- チェックリスト（`- [ ]`）は残し、実際に満たしたものだけ `[x]` にする。やっていないことにチェックを入れない
- テンプレート内のHTMLコメント（`<!-- 〜 -->`）は記入の指示として読み、その指示に従って書く。書き終えたらコメントは消してよい（リポジトリの慣習で残すなら残す）
- 該当しない見出しは削除せず、「該当なし」と一言書く（テンプレートの構造を保つため）

## 書き方

### 書く順番

1. テンプレートの全セクションについて、集めた材料をもとに**原文**を書く。省略・要約をせず、具体的な事実をすべて入れる
2. 原文をセクションごとに読み返し、**要約**を作る。要約は原文の内容を縮めたもので、新しい情報を足さない
3. 要約を各見出しの下に置き、原文はまとめて本文の一番下の `<details>` に置く

### 各見出しの下（要約）のルール

- **原文の要約であること。** 原文にない事実・推測・評価を足さない。原文と食い違うことを書かない
- **見出しの下には `<details>` を置かない。** 原文は一番下にまとめる
- **最初の1文で、その見出しの問いに直接答える。** 「概要」なら何が変わるか、「背景」ならなぜ必要か、「確認方法」なら何をすれば確かめられるか
- **機能と目的から書く。** 関数名・ファイル名・ライブラリ名を先に並べない。必要なら、説明の後に添える
  - ✕「`useAuth` に `refreshToken` 処理を追加」
  - ○「ログイン状態が1時間で切れていた問題を直し、自動で更新されるようにしました（`useAuth` に処理を追加）」
- **「何をしたか」だけでなく「なぜ」と「その結果どうなるか」を書く。** 作業ログ（〜を修正、〜を追加、の羅列）にしない
- **前提知識のない人に通じる言葉で。** チーム内の略語やセッション中にだけ使った呼び名は使わない
- **事実と推測を分ける。** 確認していないことは「未確認」と書く。テストを実行していないのに「動作確認済み」と書かない
- 箇条書きは1項目1行を目安に、3〜5個程度に収める。それ以上の詳細は原文にだけ書く
- 原文が1〜3行で、要約しても短くならないセクション（例：「完了条件」「影響範囲」）は、原文と同じ文をそのまま書いてよい

### 原文（一番下の `<details>`）の中に入れるもの

原文は全セクションの全文なので、要約に書いた内容も含めて、次のようなことを省略せずに書く。

- 要約に書いた事実・理由・結果の、元になった具体的な内容（数値、確認結果、根拠）
- ファイルごと・関数ごとの変更内容
- 検討して却下した案と、却下した理由
- コードからは読み取れない前提条件や制約、ハマった点
- 実行したコマンド、テストやログの詳細
- 次に作業するAIへの指示（触ってはいけない箇所、守るべき規約、残っているTODO）

原文は人間向けに噛み砕かなくてよいが、ファイルパス・関数名・条件は省略せず具体的に書く。原文だけを読んでも、要約なしで内容が分かるように、文として完結させる。

### 原文の置き方

- 本文の一番最後に、`---`（区切り線）を挟んで `<details>` を**1つだけ**置く
- `<summary>` の文言は `📄 原文` に統一する
- 中は**テンプレートと同じ順番で、全セクションを並べる**。短いセクションや「該当なし」のセクションも省かない
- 各セクションの原文の先頭に、**どのセクションの原文かを `#### 【見出し名】` の形で書く**。見出し名はテンプレートの文言をそのまま使う
- `</summary>` の直後と `</details>` の直前、各 `####` の前後に**空行を入れる**（ないとGitHub上でMarkdownが崩れる）

```markdown
## 概要

ログイン状態が1時間で切れていた問題を直し、操作中は自動で更新されるようにしました。

## 変更内容

期限が切れる少し前にログイン状態を自動で更新する処理を追加しました。期限切れ後に再ログインさせる案は、入力中のデータが消えるため採用していません。

## 確認方法

ログインしたまま1時間以上操作し、ログイン画面に戻されないことを確認します。

---

<details>
<summary>📄 原文</summary>

#### 【概要】

ログインのアクセストークンは有効期限が1時間で、期限が切れると操作中でもAPIが401を返し、ログイン画面に戻されていた。これを、期限の5分前にトークンを自動で更新する方式に変えた。

#### 【変更内容】

- `src/hooks/useAuth.ts`：`refreshToken()` を追加。トークンの有効期限の5分前（`AUTH_REFRESH_MARGIN`）に実行する
- 却下した案：期限切れ後に再ログイン画面へ戻す。フォームに入力中のデータが消えるため採用しない
- 注意：`AUTH_REFRESH_MARGIN` は他の画面でも参照しているので変更しない

#### 【確認方法】

ログインしたまま1時間以上操作し、ログイン画面に戻されないことを確認する。E2Eは `e2e/auth-refresh.spec.ts` で、トークン期限を短くした設定で実行する。

</details>
```

### 秘密情報

APIキー、トークン、社内URL、個人情報は、原文の中でも書かない。

## 書いた後の確認

提出前に、次を確認する。

- 見出しの下の要約だけを読んで、このリポジトリを初めて見た人が何が・なぜ変わるのか分かるか
- 原文を開かなくても、レビュー・判断ができるか
- 要約に、原文にないことや原文と食い違うことが書かれていないか
- 原文に全セクションがテンプレートの順番で揃っていて、それぞれ `#### 【見出し名】` が付いているか
- 原文だけを読んで、各セクションの内容が省略なく分かるか
- テンプレートの見出しが元のまま残っているか
- 確認していないことを、確認済みのように書いていないか

## テンプレートがない場合

次の見出しで書き、上の「書き方」に従う。

```markdown
## 概要
## 変更内容
## 確認方法
## レビューしてほしい点
```
